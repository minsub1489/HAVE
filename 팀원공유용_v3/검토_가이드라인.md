# HAVE 모델링·설계 과제 검토 가이드라인

2026-11-23 · 대상: `팀원공유용` 폴더와 `9조_HAVE_프로젝트 계획서(시스템 개발 제안 요청서)_1123.pptx` · 기준: 강의 PDF 본문과 주석(Ch05-2 ~ Ch10, 보조 PDF 3개), 과제 요구 사항 11개 항목

과제 필수 11개 항목은 모두 들어 있다. 아래는 강의 주석과 본문 기준으로 고칠 곳이다. 고친 결과물은 모두 `팀원공유용_v2` 폴더에 넣는다. 진행 상태는 맨 아래 표에 적는다.

검토 방법: 주석은 PDF에 박혀 있는 형태라, 주석이 달린 강의 PDF를 `원본` 폴더의 주석 없는 판과 겹쳐 보고 달라진 쪽을 모두 읽었다. 다이어그램 사이 일관성은 다이어그램 소스 파일과 클래스 다이어그램 그림의 글자를 대조해서 확인했다.

## 1. 주석에 "반드시·감점"으로 적힌 것 (가장 급함)

1. **배치 다이어그램이 없다.** Ch10 p54 주석이 "이 그림 반드시 표현"인데 팀원공유용에도 pptx에도 없다.
   - 그릴 내용: 사용자 PC(Chrome + 확장 프로그램), 검증자 기기(브라우저), HAVE 서버, DB, 파일 저장소, 알림 채널 노드와 그 사이의 통신 경로(HTTPS·JDBC).
2. **유스케이스별 상태 다이어그램이 부족하다.** Ch07 part1 p3 주석은 "각 유즈케이스별로 시퀀스, 상태 다이어그램 그리고, 전체 클래스 다이어그램 하나"다.
   - 순서 다이어그램(UC별)과 통합 클래스 다이어그램은 충족한다.
   - 상태 다이어그램은 UC01·UC02 두 장과 객체별 5장뿐이고, UC08·UC09에 대응하는 그림이 없다.
   - 최소한 "유스케이스 ↔ 상태 다이어그램 대응표" 1쪽이 필요하고, UC08은 따로 그리는 편이 안전하다.
3. **디자인 패턴을 4개로 줄인다.** 싱글톤·브리지·옵서버·전략만 남긴다. (Ch07 part2 p14 주석 "추상팩토리는 없을 정도로 체크해야 하고, 브리지는 점진적 개발 경우에만 적용, 어댑터는 우리에게 해당 X, 옵서버 패턴은 있을 수 있음", p16 주석 "프로젝트에 전략 패턴 반드시 적용")
   - **어댑터: 삭제.** 패턴 이름만 떼고, 실제로 하던 일은 남긴다.
     - 결과물 PDF를 저장하던 `StorageFileStoreAdapter`는 `StorageFileStore`로 이름만 바꾼다.
     - 알림 발송은 `NotificationGateway`가 직접 맡는다.
   - **추상 팩토리: 삭제.** 이 패턴은 서버가 시작할 때 운영용·테스트용 부품 묶음을 골라 조립하던 장치였다.
     - UC01~UC10 흐름, DB 테이블, 크롬 확장 프로그램에는 등장하지 않아서 사용자 기능은 줄지 않는다.
     - 없어지는 것은 테스트용 묶음을 한꺼번에 바꾸는 개발 편의뿐이다. 저장소 구현(`JdbcPersistence` / `StubPersistence`)은 서버 조립 지점(`HaveServerBootstrap`)이 설정값으로 고른다.
   - **브리지: 유지.** 강의 p10의 적용 조건(점증적 통합, 완성 전 스텁)과 근거가 맞다.
   - **전략**("반드시 적용")과 **옵서버**("있을 수 있음")는 유지한다.
   - 뺀 두 패턴은 패턴 문서에 "검토했지만 적용하지 않은 패턴"으로 이유를 남긴다.
   - 함께 고칠 산출물은 6절에 정리했다.
4. **문장에 주어가 없다.** Ch06 p38 주석이 "주어? 동사?>> 없는 팀은 감점"이다.
   - 이 주석은 클래스를 찾을 때 쓰는 요구 문장 옆에 달려 있다. 우리 문서에서 거기에 해당하는 것이 유스케이스 명세의 기본 흐름이다.
   - 기본 흐름 45단계 중 31단계에 주어가 없다(예: "새 작업을 선택한다."). 강의 예시는 "학생이 …을 선택한다 / 시스템이 …"처럼 주어를 쓴다.
   - pptx의 명세 표(37~38쪽)도 같은 문제가 있다.
   - 요구 문장에서 클래스 후보, 연관, 속성으로 이어지는 도출 과정 쪽도 없다(같은 주석이 시험 출제를 언급한다).

## 2. 다이어그램 사이 일관성 (Ch06 p61~63 본문 체크 항목)

5. **순서 다이어그램의 클래스가 통합 클래스 다이어그램에 없다.** 서비스 10종(RiskService, ReviewService, ApprovalService 등), 화면 클래스, 인터페이스(IWorkVersion 등)와 그 오퍼레이션(assessRisk, submitReview, retryIssue, verify 등)이 빠져 있다. 서비스·인터페이스를 담은 패널을 클래스 다이어그램에 추가해야 한다.
6. **상태 전이 이름이 클래스 메서드와 다르다.**
   - Review 상태: 전이는 `submitReview`·`requestRevision`인데 클래스 메서드는 `completeReview()`·`requestChanges()`다.
   - ReviewRequest: 전이는 `requestReview`·`cancelRequest`인데 메서드는 `request()`·`cancel()`이다.
   - 작업 버전 상태 ①의 전이 11개는 모두 WorkVersion 클래스에 메서드가 없다.
   - ApprovalCase·Approval·Revision·ShareLink는 맞다.
7. **UC01·UC02 순서 다이어그램(1104 원본)의 표기가 다르다.** 라이프라인이 `Controller`, `Service`로만 적혀 있어 다시 그린 UC01·UC02 클래스 다이어그램(WorkController 등)과 이름이 안 맞는다. UC03~UC10처럼 `:클래스` 형식도 아니다.

## 3. DB

8. **데이터 형식이 없다.** Ch09 p35 주석은 "클래스 다이어그램 활용해서 데이터 형식 정하고 FK 정하면 됨"이고, 강의 예시는 `OrderID: INT <<PK>>` 형식이다. 최종 스키마 표와 DB 다이어그램에 열 이름만 있고 형식이 없다.
9. ~~코드 설계(Ch09 p36~40)가 pptx에 없다.~~ **(11-23 재검토: 필수 아님, 하지 않음)** 과제 제출 항목 11개에 없고, Ch09 코드 설계 쪽(36~40)의 주석도 요구하지 않는다. 37쪽은 예시 이름 정정("우편번호" → "주민"), 40쪽의 빨간 주석은 과제 전체(HCI·DB 설계, 제출 일정, 구현 화면 캡처)에 대한 말이고, 형광펜은 시험용 강조로 본다. 코드 값은 DB 문서 부록 A에 이미 있다.
   - ERD 형식(사각형·마름모·1/N)과 "테이블화, FK, 중복 제거, 3차 정규형" 절차(Ch09 p40 주석)는 충족한다.

## 4. 구조유형·디자인 패턴·HCI 보강

10. **비기능 요구가 드러나지 않는다.** Ch07 part1(수정판) p6 주석이 "비기능 요구 사항 위주로"다.
    - P1~P7은 구조유형 문서 1절의 "풀어야 할 문제" 표다(pptx 100쪽).
    - 이 표에 "품질 속성" 열을 추가한다. P3·P4는 보안·무결성, P6는 신뢰성, P7은 유지보수성에 해당한다.
11. **MVC 판단이 애매하다.** "가능한 게 있다면 여러 개 반드시 선택"(p16 주석), MVC는 "인터랙티브 앱을 만들 경우 사용"(p17 주석)인데, 표에는 "클라이언트 화면 구성에만 해당"이라고만 적혀 있다. 확장 프로그램은 model.js(Model)와 화면 스크립트(View·Controller)로 나뉘어 있으니 "부분 채택"으로 적을 수 있다.
12. **추적표가 없다.** 주석 "유스케이스>>기능>>컴포넌트>>아키텍처 간의 연결"은 `Ch06_요구 모델링_정적동적final_261019_110420.pdf` 14쪽에 있다(`final (1)` 파일에는 없다). 유스케이스, 오퍼레이션, 인터페이스·컴포넌트, 계층을 잇는 표 1쪽이 필요하다.
13. **패턴 쪽 칸 구성을 강의 표에 맞춘다.** 출처는 `Ch07_아키텍처-part2` 5쪽(형식)과 8쪽(이름·문제·해결책·결과 표)이다.
    - 예제·코드는 pptx에 넣지 않는다. (5쪽에서 "예제"도 형광펜 항목이다.)
    - 남는 일은 두 가지다. 칸 이름을 문제·해결책·결과로 맞추고, 지금 없는 "결과" 칸을 추가한다.
    - "선택한 이유" 칸은 과제 요구라서 그대로 둔다.
    - 패턴 문서(md·pdf)에 이미 있는 예제 코드는 그대로 둔다.
14. **HCI에 강의 항목 3가지가 없다.**
    - 피드백(Ch08 p12 주석 "디자인에 반드시 포함"): 구현에는 있지만(알림 토스트, 5단계 진행 표시, 발급 중·실패 상태) pptx에서 따로 보여 주지 않는다.
    - 태스크 분석(p28 "유스케이스 별로 UI 흐름"): 유스케이스별 화면 흐름도가 없다.
    - 입력 설계와 입력 오류 체크(p43~46): 선택 상자, 20자 이상, PDF·20MB 검사처럼 구현은 되어 있지만 pptx에 정리돼 있지 않다.

## 5. 이미 충족하는 것

- 과제 11개 항목 모두 있고, 클래스 다이어그램 수정본에 빨간 상자가 표시돼 있다.
- 유스케이스별 순서 다이어그램, 통합 클래스 다이어그램, 패키지 레벨 2·3(주석 "레벨2, 3 만들고"), 컴포넌트 제공·요구 인터페이스가 있다.
- 구조유형 쪽에 목적·이슈·선택 이유가 있다(주석 "ppt에 설명").
- 브리지·옵서버·전략 패턴은 주석과 맞다.
- 실제 구현 화면 캡처가 있다(Ch09 p40 주석 "실제로 구현해서 화면 캡처하고"). 11-23에 출처를 Ch10에서 Ch09로 바로잡았다.
- extend 방향과 조건, 유스케이스 ID(주석 "+아이디")가 맞다.
- 오퍼레이션 이름 214개를 검사했는데 철자 오류는 없었다(Ch06 주석 "스펠링 틀리면 감점").
- **명명 규칙은 지금 해석을 유지한다.** is·get·set으로 시작하는 이름이 42개, 동사로 시작하는 이름이 58개다.
  - Ch10 p11("메소드는 동사구, 필드 값은 get, bool은 is")과 보조 PDF의 `makeOrder()` 예시 기준으로는 충족한다.
  - Ch06 p23 주석 "is get set show로 반드시 시작"을 글자 그대로 읽으면 58개가 걸린다.

자잘한 것으로, UC06 명세는 "승인 조건 4개"인데 확장 프로그램과 1123 수정 내역은 5개다.

## 6. 패턴 정리(3번)로 함께 고칠 곳

타입 처리는 다음과 같다. 삭제 6개, 이름 변경 1개라서 서버 타입은 **85개에서 79개**가 된다.

| 타입 | 처리 | 이유 |
| --- | --- | --- |
| InfrastructureFactory, ProductionInfraFactory, LocalStubInfraFactory | 삭제 | 추상 팩토리 자체 |
| InMemoryFileStore, ConsoleNotifyChannel | 삭제 | 테스트 묶음에만 쓰던 부품 |
| EmailNotifyChannel | 삭제, 일은 NotificationGateway가 맡음 | Gateway → Channel 구조가 강의의 어댑터 그림과 같음 |
| StorageFileStoreAdapter | 이름만 `StorageFileStore`로 변경 | `FileStore`를 구현해 결과물 PDF를 실제로 저장 |
| NotificationGateway | 유지, "어댑터" 설명만 삭제 | 1109 원자료 클래스, 알림 발송과 알림함 저장 |
| HaveServerBootstrap | 유지 | 옵서버 등록, 저장소 구현 선택 |

결과물 저장, 알림 발송, DB 저장, 테스트용 스텁 DB(`StubPersistence`)는 모두 남는다. 컴포넌트 다이어그램의 외부 시스템 "알림 채널"과 "파일 저장소"는 실제로 연결되는 바깥 시스템이라 그대로 둔다.

| 산출물 | 바꿀 내용 |
| --- | --- |
| 09 디자인 패턴 문서 | 어댑터·추상 팩토리 장을 "검토했지만 적용하지 않은 패턴"으로 바꿈, 요약표·배치 그림·패턴 관계·추가 타입 목록 수정, 싱글톤·브리지 본문의 "추상 팩토리가 고른다" 문구 수정 |

| 06 패키지 레벨 2·3 | 6개 타입 제거와 이름 변경 1개, 서버 타입 수 85개에서 79개로 |
