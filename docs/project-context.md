# HAVE 프로젝트 맥락과 작업 인수인계

마지막 대조: **2026-10-28, Asia/Seoul**. 저장소의 발표자료 1~11쪽, README, 아키텍처·모델링 문서, 웹·확장 소스와 도메인 테스트를 확인했다. 이 문서는 다음 작업을 시작할 때 읽는 안내다. 기능 구현 상태가 바뀌면 날짜와 근거를 함께 갱신한다.

## 1. 프로젝트의 목적과 사용자

**HAVE(Human Approval & Version Evidence)**는 팀원·문서·대화·AI 작업 기록에 흩어진 지식을 연결해, 팀이 작업을 함께 이해하고 설명·수정·인수인계할 수 있게 하는 협업 프로젝트다. 저장소·화면·코드의 **HumanProof**는 같은 프로젝트의 프로토타입 명칭이다.

팀원이 각자 전문 지식을 갖는 것은 협업의 자연스러운 분업이다. 중요한 결정의 이유를 찾기 어렵거나, 서로 다른 가정을 사용하거나, 특정 사람 없이는 변경을 검증하기 어려워지면 팀에 지식 부채가 쌓인다. AI 에이전트로 만든 결과를 빠르게 채택하면서 사람이 이유와 영향 범위를 확인하지 못할 때도 같은 문제가 생긴다.

2026-11-16 사용자 방향 확인. 제품은 **핵심 맥락 연결 → 작성자의 이해 확인 → 팀원의 재현·인수인계 → 변경 시 재확인**을 지원하는 방향으로 발전시킨다. 검토·승인 증명은 **누가 어떤 파일 버전의 어느 범위를 어떤 근거로 확인했는지** 추적하게 한다. 현재 로컬 흐름은 `PDF·AI 사용 신고 → 이해 과제 → 인간 검토·승인 → 증명서·QR 확인 → 변경·철회·파일 비교`다. [설계 제안과 점검 시나리오](knowledge-debt.md) 및 [연구 근거](knowledge-debt-research.md)를 참고한다. 문항 구성, 인수인계 과제, 지식 부채 수명주기는 설계 후보이며 프로토타입 구현 상태는 3절과 6절을 따른다.

발표자료의 초기 적용 대상은 대학 팀 프로젝트이며, 수업 운영자·조교, 연구실·소규모 팀을 도입 주체 후보로 둔다. 사용자 조사·효과 측정·가격/지불 의사 검증은 수행 전이다. 경제성 수치와 일정은 발표의 가정이며 실제 매출·검증 결과·새 작업의 확정 제약으로 사용하지 않는다.

승인 기록은 **검토 절차와 판단 근거의 기록**이다. 실제 이해, 문서의 사실 정확성, AI 사용 신고의 진실성을 보증하는 서비스라고 설명하지 않는다. 파일 해시는 바이트 동일성을 확인하며, 그 자체로 승인자 신원이나 증명서 진위를 인증하지 않는다.

근거: [발표자료](<presentation/HAVE_프로젝트 계획서(시스템 개발 제안 요청서).pptx>) 2·4~9·11쪽, [아키텍처](architecture.md), [모델링 기준](modeling/README.md).

## 4. 현재 역할과 전체 서비스 역할

현재 MVP의 액터는 **작성자, 검토자, 검증자/수신자**다. 검토자 B가 평가와 최종 승인을 함께 수행한다. 작성자 A·검토자 B 역할 전환은 시연이며 실제 사용자 인증·작업별 멤버십·서버 권한 검사가 아니다.

전체 서비스 원본에는 **독립 최종 승인자, 시스템 관리자, 열람자/팀원**도 있다. 향후 이 역할들을 구현할 때 현재 검토자와 무조건 합치지 않는다. 독립 최종 승인자를 실제로 둘지, 작업별 겸임과 권한을 어떻게 허용할지는 제품 범위와 권한 정책으로 정한다.

Chrome 확장과 서버/Outbox 작업자는 HAVE 전체 경계에서 내부 구성요소다. 별도 배포/실행 경계와 외부 액터는 다른 개념이다. 웹 API만을 대상으로 하는 별도 연동도에서는 시스템 경계를 명시하고 확장 클라이언트를 표현할 수 있다. 실제 자동 AI 평가 API는 없으므로 현재 모델에 AI 평가 서비스를 새 외부 액터로 가정하지 않는다.

## 6. 구현·설계에서 보존할 도메인 규칙

### 승인 대상과 버전

- 승인은 작업 제목이나 파일명 전체가 아니라 **특정 version ID, PDF SHA-256, AI 신고, 검토 스냅샷**에 고정된다. `reviewDigest`는 정책·과제 답변/평가·체크·메모·기여를 묶는다.
- 파일·AI 신고·위험 입력을 변경하면 새 버전으로 등록한다. 같은 PDF라도 신고 내용이 달라지면 새 버전일 수 있다. 승인 후 답변·평가·기여·체크·메모는 수정하지 않는다.
- 새 버전은 이전 승인을 상속하지 않는다. v1의 승인 기록은 남고 v2는 별도 과제·검토·승인이 필요하다.
- 현재 단일 검토자 MVP는 **버전당 승인 최대 한 건**이다. 철회 후 같은 버전을 다시 승인하지 않는다. 재승인은 새 버전으로 진행한다. 복수 승인자는 미구현 확장 범위다.

### 이해 과제와 승인 조건

- 과제는 **Teach-back, Fault Injection, What-if 세 종류 고정**이다. 위험 점수는 참고 입력이며 현재 과제 수/종류를 자동 변경하지 않는다.
- 과제당 0~2점, 총점 **5/6 이상**, 세 답변 제출, 모든 평가 근거, 치명 오류 없음이 필요하다. 발표의 70% 기준을 정수 점수로 적용한 결과다. 자기 확신도는 합격 점수가 아니다.
- 체크리스트 네 항목, 최종 검토 메모, 검토자 시연 역할, 수정 요청 해제, 기존 승인 없음, 저장 가능 여부도 확인한다. 점수 통과만으로 승인 완료가 되지 않는다.
- 실제 조건은 `domain.js:gatesPassed`, `app.js:approvalReasons`, 승인 동작을 함께 본다. 도메인 판정 함수 하나만 수정하고 화면·저장 경로의 다른 조건을 남겨 두지 않는다.

### 재검토·철회·상태

- 수정 요청은 이전 검토 회차를 보존하고 현재 평가·체크·메모를 초기화한다. 작성자가 답변을 보완하고 모두 다시 제출한 뒤 재평가한다.
- 기여 근거 추가도 검토 범위를 변경하므로 기존 평가·체크·메모를 초기화한다. 이 경우 이미 제출된 답변까지 자동으로 미제출되는 것은 아니다. 승인된 버전에는 근거를 추가할 수 없다.
- **검토 완료와 승인 완료, 승인 철회와 후속 버전 존재**를 구분한다. 철회와 후속 버전 존재는 동시에 성립할 수 있다. 현재 UI 배지는 여러 차원을 우선순위로 요약한 결과다.
- 철회는 원본 승인 삭제가 아니라 시각·사유가 추가되는 단방향 변경이다. 현재 UI는 최근 승인을 선택한다. 운영 서비스의 승인 ID 선택과 철회 권한은 별도 정책이 필요하다.

### 저장·기여 입력·공개 검증

- 현재 작업 전체와 승인·감사 변경은 IndexedDB의 원자적 저장으로 묶인다. 성공 표시/알림은 commit 이후다. 저장 실패 시 복원하고 입력 백업을 제공한다.
- revision 충돌은 최신 상태를 확인하는 경로로 처리한다. 충돌한 승인을 자동 재시도하지 않는다. 손상 데이터는 자동 삭제하지 않고 복구 경로를 둔다.
- 기여 JSON은 **사용자 신고 데이터**이며 승인 명령이 아니다. 검증·미리보기·명시적 확인·ID 중복 제거를 거쳐 연결한다. 주입된 역할/명령 필드를 신뢰하지 않는다.
- 현재 PDF 상한은 20 MiB(화면 표기 20 MB)다. 확장의 저장 기록은 최대 100개, 웹 가져오기 JSON은 최대 1 MiB이며 입력 개수·길이·URL도 검증한다. 바꿀 때 확장·웹·도메인·테스트의 계약을 함께 확인한다.
- 현재 QR은 **전자서명 없는 발급 당시 공개 요약**이다. 해당 기록을 가진 브라우저에서만 로컬 철회·후속 버전을 확인할 수 있다. 다른 기기에서 최신 상태를 확인했다고 표시하지 않는다.
- 파일 비교는 사용자가 파일을 선택했을 때 실행하는 선택적 동작이다. QR 열기만으로 파일이 일치한다고 표시하지 않는다. 승인 진위·현재 효력·파일 일치는 서로 다른 결과다.
- 공개 화면에는 비공개 과제 답변·평가·검토 메모를 포함하지 않는다. 공개 필드는 `publicRecord`를 기준으로 확인한다. 로컬 해시 체인만으로 독립 감사·전체 이력 보존까지 입증한다고 설명하지 않는다.

근거: [도메인 규칙](../prototype/dist/domain.js), [화면·워크플로](../prototype/dist/app.js), [저장소](../prototype/dist/repository.js), [확장 데이터 계약](../extension/records.js), [도메인·확장 테스트](../tests/domain.test.cjs).

## 8. 실행과 변경 유형별 검증

저장소 루트에서 실행한다. 웹 빌드·구문 검사·순수 도메인 테스트는 추가 npm 패키지가 필요하지 않다. 브라우저 검사와 그림 렌더링은 Playwright 및 Chrome 실행 환경이 필요하다. 이 프로젝트는 현재 HTML/CSS/JavaScript·Node 스크립트 저장소다.

```sh
# 웹 시연 서버: http://127.0.0.1:4173/
node scripts/serve.cjs

# 웹 원본을 단독 HTML로 생성
node scripts/build-standalone.cjs

# 도메인·확장 데이터 규칙
node --test tests/*.test.cjs

# 구문 검사: 네 명령을 각각 실행하거나 npm run check 사용
node --check prototype/dist/app.js
node --check prototype/dist/domain.js
node --check prototype/dist/repository.js
node --check extension/popup.js

# 실제 브라우저 흐름 / 확장 팝업 모의 API: 각각 실행
node tests/browser.cjs
node tests/extension-browser.cjs
```

`npm start`, `npm run build`, `npm run check`, `npm test`, `npm run test:browser`도 `package.json`에 정의되어 있다. npm이 없는 환경에서는 위 Node 직접 명령을 사용한다. Playwright가 기본 모듈 경로에 없으면 해당 환경의 `NODE_PATH`를 사용한다. 설치된 Chrome 위치가 필요하면 `CHROME_EXECUTABLE`을 지정한다. 다른 작업 환경의 절대 캐시 경로를 저장소 설정에 고정하지 않는다.

| 변경 유형 | 필요한 확인 |
| --- | --- |
| 문서만 변경 | 로컬 링크, 근거 파일/함수 존재, 범위·용어·번호 일치, Git diff/공백 검사. 제품 빌드·브라우저 테스트는 별도 필요가 있을 때 실행한다. |
| 도메인·저장·웹 동작 | 영향받는 구문 검사, 기존 도메인 테스트, 해당 브라우저 흐름. 웹 원본이 바뀌면 단독 HTML 생성도 확인한다. |
| 실제 Chrome 확장 | 데이터·Manifest 테스트와 팝업 모의 API 테스트. 실제 activeTab 권한·툴바 호출은 `extension/README.md`의 설치 후 수동 점검으로 확인한다. |
| 다이어그램 | 해당 원본에서 렌더링, 이미지의 글자·선·경계 직접 확인, 상세 모델·코드·번호 추적성 대조. 무관한 PDF/PPT를 자동 재생성하지 않는다. |

회귀 시나리오는 정상 승인, 조건 불충족 차단, 수정 요청/재제출, 기여 변경 후 재평가, v2 승인 미상속, 철회, 정상/변경 PDF 비교, 다른 기기의 QR 확인 범위, 저장 실패·동시 탭 충돌·손상 데이터 복구를 기준으로 선택한다. 실행하지 못한 환경/검사는 결과에 남긴다.

다이어그램 명령과 의존성은 [모델링 편집 방법](modeling/README.md)을 따른다. 최적화 개요만 바꾸면 `node docs/modeling/optimized/render.cjs`를 사용하고 필요 시 `DIAGRAM_NODE_MODULES`를 지정한다. 이 경로는 기존 갤러리/PDF를 재생성하지 않는다.

## 9. 실제 서비스로 이어갈 때의 설계 출발점

아래는 [기존 아키텍처의 권장 순서](architecture.md)의 요약이며 **미착수 설계 제안**이다. 이번 문서 작성이 서버 개발 착수나 기술스택 확정을 의미하지 않는다.

1. **계정·작업 멤버십·비공개 접근**: 실제 신원, 작성자/검토자 배정, 자기 승인 금지를 서버에서 검사한다. 역할 전환 시연을 인증 기반으로 재사용하지 않는다.
2. **버전·검토·승인 저장**: 버전/검토 스냅샷, 회차, 승인 유일성, 예상 revision, 멱등 요청, 승인·감사·Outbox 원자적 기록을 정의하고 검증한다.
3. **서명 영수증·최신 상태 조회**: 업무 승인과 서명 준비 상태 `PENDING/READY/FAILED`를 분리한다. 같은 receipt ID/payload로 재시도하며 서명 실패를 승인 취소로 혼동하지 않는다. 공개 검증은 조회 시각·진위·현재 효력·파일 일치를 구분한다.
4. **운영 가능한 파일 저장·복구·관측**: 파일과 메타데이터 분리, 서버 전체 바이트 해시, 비공개 저장소와 업로드 생명주기, 실패 객체 정리, 백업/복구, 모니터링·키 수명주기·보존 정책을 구체화한다.

모듈형 단일 API, PostgreSQL, 비공개 객체 저장소, Outbox, 서명키 관리는 기존 문서의 제안이다. 서버 프레임워크·실제 호스팅·계정 제공자·서명/정규화 라이브러리의 선택은 이번 작업에서 검증·확정하지 않았다. 신규 구현을 시작할 때 현재 환경과 의존성 문서를 다시 확인한다.

블록 편집·의존관계, 독립 최종 승인자, 복수 승인, 위험별 동적 과제, Human Edit/Micro Defense, 자동 AI 평가 보조, 확장 API 업로드, 알림·공개 통계, 승인 지식 검색·재사용은 전체 요구/확장 후보로 유지한다. 구현 우선순위와 수용 기준을 정하기 전 완료 기능 목록에 넣지 않는다.

| 운영·제품 검증 | 사용자 조사·가격·효과 측정은 수행 전이다. | 대상 수업/팀, 사용 시나리오, 측정 계획, 비용/호스팅 제약 |

이 항목들은 현재 미정이라는 맥락이다. 작업을 막는 승인 목록이 아니다. 기존 지시와 근거로 판단할 수 있는 구현 선택은 진행하고, 제품 범위·권한처럼 사용자 결정이 필요한 차이는 구체적으로 설명한다.

다음 작업은 먼저 Git 상태와 관련 원본을 확인하고, 새 요구가 현재 기능/운영 설계 중 어디에 해당하는지 판단한다. 변경 후에는 관련 코드·모델·설명·생성 산출물의 일치 여부를 확인하고 필요한 검증 결과를 남긴다. 현재 범위나 주요 결정이 바뀌면 이 문서와 해당 상세 문서를 함께 갱신한다.

이번 문서 추가 시 제품 코드는 변경하지 않았다. 관련 문서 5개의 로컬 링크 56개, 모델의 근거 파일/식별자, 원본 52개 대응표의 누락·중복을 확인했다. 원본 이미지 사본은 사용자 첨부와 SHA-256이 일치했다. 제품 테스트는 문서 전용 변경이라 새로 실행하지 않았다. 다음 갱신 시에도 실제로 수행한 검사와 수행하지 않은 검사를 구분해 기록한다.

같은 날 후속 UML 모델링 작업에서는 새 10개 그림·13쪽 PDF의 렌더링과 모델 간 참조, 관련 문서 링크 74개를 확인하고 기존 도메인 테스트 17개를 실행해 통과했다. 공통 렌더러의 함수 재사용 변경은 기존 SVG 13개를 메모리에서 재생성해 결과가 같음을 확인했다. 이번 후속 작업도 제품 코드와 운영 구현 범위를 바꾸지 않았다.

2026-10-28 모델 갱신: 다중도 10개를 코드·유스케이스 조건과 대조하고 경계 사례 18개를 `audit_constraints.cjs`로 확인했다. 수정 원본은 기존 `uml/model.json` 및 `optimized/use-cases.json`이며 설명 파일은 `export_contracts.py`로 생성한다. 부분 렌더링 명령으로 C01·C02·ST01·ST02만 갱신할 수 있다. 전체 UML PDF는 현재 14쪽이며 상태·다중도 상세 PDF는 7쪽이다. 제품 코드와 실제 저장 형식은 바꾸지 않았다.
