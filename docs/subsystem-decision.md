# HAVE 서브시스템 결정

## 확정 서버 패키지

사용자가 확정한 8개 서버 서브시스템을 현재 기준으로 사용한다. 번호는 정의서 순서를 따른다.

- 레벨 2는 서버 서브시스템과 공통 의존을 표시한다. [PNG](modeling/integrated/images/HAVE_서버_패키지_8개.png) · [SVG](modeling/integrated/images/HAVE_서버_패키지_8개.svg)
- 레벨 3은 각 서브시스템의 내부 패키지와 타입 배치를 표시한다. 통합 클래스의 55개 타입 중 사용자 화면 ReviewPage와 RevisionPage를 클라이언트에 두고 서버 타입 53개를 한 번씩 배치했다. [PNG](modeling/integrated/images/HAVE_서버_패키지_8개_레벨3.png) · [SVG](modeling/integrated/images/HAVE_서버_패키지_8개_레벨3.svg)

| 번호 | 패키지 | 주 담당 범위 |
| --- | --- | --- |
| 01 | Auth · 사용자·권한 관리 | 공통 인증·권한 |
| 02 | Work · 작업·결과물 관리 | UC01·02·05, 수정본의 새 버전 생성 |
| 03 | Review · 검토 관리 | UC03·04, 검토 요청·피드백·보완 판정 |
| 04 | Approval · 승인 관리 | UC06·10, 승인·반려·철회 결정 |
| 05 | Certificate · 증명서 관리 | UC07, UC06 성공 이후 증명서 발급·조회·공유 |
| 06 | Verification · 진위 검증 | UC08, 서명·파일 해시·현재 효력 확인 |
| 07 | Audit · 이력 관리 | UC09, 공통 이벤트 기록과 검토·보완·재제출 알림 |
| 08 | Persistence · 데이터 저장 | 공통 데이터·파일 영속화와 저장 일관성 |

패키지 화살표는 사용하는 쪽에서 제공하는 쪽을 향한다. Work의 UC05는 수정본의 새 버전을 생성하고, 재검토 요청은 Review에 전달하는 흐름으로 정리했다. Certificate는 성공한 승인 결과와 고정된 버전을 Approval에서 읽어 발급한다. Verification은 Certificate에서 서명 데이터를 읽고 Approval에서 현재 철회 효력을 확인한다. 핵심 업무와 공통 지원 묶음은 그림을 읽기 위한 구획이다.

## 이전 6개 분류안

UC01~UC10 운영 설계의 기준은 **업무 서브시스템 5개와 공통 기반 1개**다. 팀의 6개 정의안을 뼈대로 채택하고, 11개 정리안의 UI·업무·지원 계층과 승인 증명서 소유 규칙을 반영한다. 서브시스템 번호는 논리적 책임 경계를 나타낸다. 운영 API는 기존 모듈형 모놀리스 구조를 따른다. [아키텍처 패턴](architecture-pattern.md)

| 번호 | 서브시스템 | 주 담당 UC | 소유 데이터와 책임 |
| --- | --- | --- | --- |
| S01 | 작업·결과물 관리 | UC01·02 | Work, WorkVersion, AI 사용 신고, 기여, 근거. 원본 등록과 새 버전 생성을 담당한다. |
| S02 | 검토·보완 관리 | UC03~05 | 검토 요청, 위험 평가, 이해 과제·답변·평가, 피드백, 수정 회차. 재제출을 조정하고 S01에 새 버전 생성을 요청한다. |
| S03 | 승인·철회 관리 | UC06·10 | 승인 결정, 승인 효력과 철회 기록, 증명서 발급 레코드, 서명 Outbox. 서명 작업자는 S03의 후속 실행 경계다. |
| S04 | 증명서 공유·진위 검증 | UC07·08 | 공유 링크와 QR, 공개 범위 및 검증 결과. 발급 레코드·서명 상태·현재 효력은 S03의 조회 계약을 사용한다. |
| S05 | 감사·이력 관리 | UC09 및 전체 변경 감사 | 추가 전용 AuditEvent, 작업별 타임라인과 현재 상태 조회 모델. 변경 명령의 트랜잭션 안에서 감사 추가 계약을 제공한다. |
| S06 | 공통 기반 | 전 UC 지원 | 사용자·작업 멤버십, 권한 판단, 해시·서명키 연동, 저장·알림 포트와 어댑터. 업무 상태의 변경 권한은 S01~S05에 둔다. |

사용자 접점은 화면과 API 진입점으로 두고 여섯 서브시스템과 구분한다. 공개 검증 웹은 링크·QR을 받는 외부 수신자의 접점이다. Chrome 기여 기록 확장은 S01의 입력 연계 접점이며, 실제 현재 확장의 연결 방식은 JSON 교환이다. DB·파일 저장소·서명키는 인프라 자원으로 표현한다.

## 합의할 경계 규칙

- **재제출과 버전 생성.** UC05의 보완과 재검토 흐름은 S02가 맡고, 버전 생성은 S01만 수행한다. 새 버전은 새 검토를 거치며 기존 버전의 승인을 상속하지 않는다.
- **증명서와 효력.** 통합 클래스의 Certificate는 UC06·10 문서에서 Receipt라고 부르는 발급 레코드다. S03이 승인·발급 레코드(PENDING)·감사·Outbox를 하나의 DB 트랜잭션으로 저장한다. S04가 이 기록을 조회하고 공개용 링크와 QR을 관리한다. 서명 준비 상태, 승인 철회, 후속 버전, 링크 만료, 파일 해시 일치는 별개로 판단한다.
- **감사와 현재 상태.** S05는 사건 순서를 감사 로그에서 읽고 현재 상태는 원본 버전·검토·승인 데이터를 읽는 조회 포트로 얻는다. S05의 조회 어댑터는 같은 DB의 읽기 뷰나 일관된 조회 스냅샷을 사용한다. 이렇게 하면 업무 모듈이 S05에 감사 기록을 요청하면서 S05가 다시 업무 모듈을 호출하는 의존 순환을 피할 수 있다. 공개 검증의 현재 승인 효력은 S04가 S03에 직접 조회한다.
- **업무 권한과 공통 기반.** S06이 인증·멤버십·권한 판정 계약을 제공하고, S01~S03이 자신의 업무 변경 트랜잭션 안에서 권한과 상태를 확인한다. 작성자·검토자·최종 승인자 역할은 작업별 멤버십으로 표현한다.

## 두 팀안에서 반영한 내용

| 팀 자료 | 반영할 내용 | 이 결정에서 조정한 내용 |
| --- | --- | --- |
| HAVE 서브시스템 정리, 2~8쪽 | UI·업무·지원 계층, 서명 준비와 승인 효력 구분, 승인 모듈의 발급 레코드 소유 | 공유와 진위 검증은 S04의 내부 패키지로, 권한·저장·알림은 S06 내부 책임으로 둔다. 감사 기록과 이력 조회는 S05에서 쓰기·읽기 계약을 분리한다. |
| HAVE 서브시스템 정의서, 2~4·8~9쪽 | 6개 책임 경계, UC05 조정과 버전 생성 분리, 클래스·상태 소유권을 기준으로 한 분류 | 발급 원본과 철회는 S03이 소유한다. S04는 공개 공유·검증을 맡고 현재 효력을 S03에서 읽는다. S05의 현재 상태는 원본 상태를 조회한다. |

레벨 2의 분해 기준은 위 S01~S06이다. 레벨 3에서는 각 서브시스템 내부 패키지를 분리한다. 특히 S04는 공유·검증, S05는 감사 추가·이력 조회, S06은 권한·무결성·저장·알림으로 펼친다. 기존 5개 기준의 그림은 이전 설계 버전이며, 이후 패키지·컴포넌트·패턴 개정은 이 결정을 기준으로 한다.
