# UC06·UC10 UML 설계

2026-11-02. 사용자가 새로 제공한 **10개 유스케이스 그림** 중 담당 범위인 **UC06 최종 승인 및 반려**, **UC10 승인 철회**만 설계한다. 그림 모음에서 여섯 종류의 PNG·SVG를 볼 수 있다. ‘동적’은 UML의 별도 단일 다이어그램 종류가 아니므로 순서·상태와 구분되는 **활동 다이어그램**으로 표현했다.

중요: 이전 `optimized/`의 9개 MVP 유스케이스와 번호가 다르다. **이 문서의 UC06은 최종 승인·반려이며, 기존 MVP UC-06은 철회다.** 새 첨부 그림의 최종 승인자를 독립 업무 역할로 유지했다. 서버·인증·권한 검사·서명 작업자는 운영 설계안이며 현재 프로토타입에 구현되어 있다는 뜻이 아니다. 기존 모델과 제품 코드는 변경하지 않았다.

## 산출물과 추적

| 한 장씩 생성 | 표현하는 내용 |
| --- | --- |
| 순서 | 좌측 UC06 승인/반려/조건 오류, 우측 UC10 철회/멱등 재요청/오류. 생명선·동기 호출·반환·alt 분기 |
| 상태 | ApprovalCase의 최종 결정과 Approval의 효력 변경을 분리한 두 상태기계 |
| 활동 | 두 UC의 요청 검사·승인/반려/철회 분기·저장·롤백을 연결한 업무 흐름 |
| 클래스 | 두 UC에서 쓰는 11개 공통 클래스의 속성·연산·연관·다중도·사용 의존 |
| 패키지 | 사용자 접점·업무 조정·도메인·권한·저장 계약의 논리 그룹과 의존 방향 |
| 컴포넌트 | 웹과 승인 API, 권한 모듈, 저장 어댑터가 제공·요구하는 인터페이스 및 DB·서명 연계 |

순서·상태·활동은 동적 모델, 클래스·패키지·컴포넌트는 정적 구조 모델이다. 이 클래스 그림은 **UC06·UC10의 통합 클래스 뷰**이며 HAVE 전체 10개 유스케이스의 최종 통합 클래스라고 주장하지 않는다.

## 유스케이스 계약

공통: 사용자는 로그인한 세션으로 식별한다. 요청 body의 역할을 신뢰하지 않는다. revision과 요청 내용에 묶인 멱등 키를 확인한다. 같은 키·같은 요청은 기존 결과를 반환하고, 같은 키·다른 내용은 거부한다. 트랜잭션 안에서 권한·revision·조건을 재확인하고, 데이터 변경과 감사·멱등 결과를 함께 commit한다.

### UC06 최종 승인 및 반려

- 사전 조건: 특정 버전의 검토가 끝나고 최종 결정 대상이 대기 중이며 담당 최종 승인자가 배정되어 있다.
- 승인 조건 A: 해당 작업의 담당 최종 승인자, 작성자와 다른 사용자, revision 일치, 대기 상태, 기존 승인 없음. 세 과제 제출·모든 평가 근거·5/6 이상·치명 오류 없음·수정 요청 해제·체크 4개·검토 메모를 확인한다. 이 수치는 기존 프로젝트의 정책을 계승한 설계 가정이며 새 첨부 그림 자체가 점수를 규정하지는 않는다.
- 승인 결과: Approval, Receipt(PENDING), AuditEvent, OutboxEvent를 한 트랜잭션에 기록한다. 성공 결과는 commit 뒤 반환한다.
- 반려 조건 J: 담당 권한·자기 승인 금지 정책·revision 일치·대기 상태·반려 사유. 점수 합격은 반려의 사전 조건이 아니다.
- 반려 결과: 결정 상태와 사유·감사를 저장한다. 승인과 증명서를 생성하지 않는다. 보완·재제출은 UC05로 넘긴다.
- 예외: 권한·조건 오류는 무변경으로 차단한다. 저장 실패는 전체 롤백, 충돌은 최신 상태 확인이며 자동 승인 재시도는 금지한다.

### UC10 승인 철회

- 사전 조건 R: 승인 ID가 존재하고 아직 철회되지 않았으며, 로그인한 사용자에게 해당 작업의 철회 권한이 있고 revision이 일치하며 사유가 있다.
- 처리: Approval.revoke가 Revocation을 만들고, 승인 효력 변경·철회자·시각·사유·감사를 함께 저장한다.
- 사후 조건: 원본 승인과 증명서는 보존한다. 철회는 단방향이며 같은 버전 재승인을 허용하지 않는다. 새 버전은 별도 검토·최종 결정 대상이다.
- 예외: 미승인·빈 사유·권한 없음은 차단한다. 동일 멱등 키는 기존 결과를 반환한다. 별도 중복 철회 요청은 기존 철회 상태를 안내한다. 저장 실패 시 기존 승인 효력을 유지한다.
- 철회 권한자의 구체적인 범위(기존 승인자 한정/작업의 담당 최종 승인자/운영 관리자 허용)는 권한 정책으로 확정해야 한다. 이 모델이 임의로 관리자 권한을 부여하지 않는다.

## 클래스 관계와 다중도

| 관계 | 한 객체를 기준으로 읽는 규칙 |
| --- | --- |
| ApprovalCase — VersionSnapshot | 결정 대상은 스냅샷 1개에 고정. 스냅샷에는 결정 대상이 0..1개 |
| VersionSnapshot — ReviewSnapshot | 최종 결정용 스냅샷은 고정 검토 결과 1개, 검토 스냅샷도 버전 스냅샷 1개에 대응 |
| ApprovalCase — Approval | 결정 대상당 승인 0..1개. 승인은 결정 대상 1개에만 속함 |
| Approval — Receipt | 승인당 발급 레코드 1개. 서명 미완료도 Receipt는 존재함 |
| Approval — Revocation | 승인당 철회 0..1개. 철회 후 관계를 지우지 않음 |
| ApprovalCase — AuditEvent | 결정 대상당 감사 사건 0..*개, 사건당 결정 대상 1개. 생성 직후 사건 0개를 허용하며 성공 결정/철회는 감사를 필수 기록 |
| Receipt — OutboxEvent | 증명서당 논리적 서명 요청 1개, 같은 요청을 재전달. 전달 시도마다 새 승인·증명서를 만들지 않음 |

이 모델의 VersionSnapshot/ReviewSnapshot은 최종 결정 순간의 불변 값 사본이다. 작업 중인 Version/Review 전체 수명주기나 현재 MVP의 중첩 저장 객체를 대체하지 않는다. `ApprovalCase`는 이 범위의 새 분석 개념이다. 반려는 이 결정 시도를 종료하고 UC05가 보완 후 새 대상 버전으로 재요청하는 설계 가정을 사용한다. 같은 버전의 여러 최종 결정 시도를 허용하기로 결정한다면 Case의 다중도를 늘리고 버전당 승인 유일성 제약을 별도로 유지해야 한다.

ApprovalCase의 APPROVED는 **승인 결정이 내려졌다는 과거 사실**이다. 이후 Approval이 철회되어도 과거 결정을 반려로 바꾸지 않는다. `/revokedAt`을 저장 조회값으로 중복 유지한다면 Revocation의 시각과 일치하도록 트랜잭션 제약을 둔다. 서명 상태 PENDING/READY/FAILED, 철회 여부, 후속 버전 존재는 서로 다른 차원이다.

## UML 표기와 범위

- 클래스 실선은 연관, 양 끝 숫자는 다중도, 점선 열린 화살촉은 사용 의존이다. 근거 없는 상속·집합·합성을 추가하지 않았다. 속성은 `-`, 공개 연산은 `+`로 표시한다. ID·시각·해시는 축약한 값 타입이며 별도 액터 클래스를 만들지 않았다.
- 순서 그림의 생명선은 객체 역할·분석 타입이다. actor는 업무 요청을 전달하는 최종 승인자이며 웹 전송 계층은 생략했다. 검토 통과는 ApprovalCase.approve의 내부 불변식으로 ReviewSnapshot.passes를 확인한다. 세부 조건은 주석에 표시했다. alt 가드는 배타적으로 해석하며, 이전 결과가 없는 경우에만 새 결정을 수행한다.
- 상태 최종 노드는 해당 절차의 종료다. 저장 데이터 삭제가 아니다. 자기 전이는 오류 후 동일 상태를 유지하는 요약 표현이며 충돌 때는 최신 저장 결과로 재동기화한다.
- 활동의 마름모는 결정/병합, 검은 원은 시작, 이중 원은 활동 종료다. 병렬 처리가 없으므로 fork/join을 넣지 않았다. A/J/R 조건은 위 계약과 같다.
- 컴포넌트의 `«component»`와 제공 인터페이스 원형·사용 의존을 구분했다. 서명 작업자는 UC06 승인 결과의 연계 대상으로만 표시한다. UC07 공유 및 UC08 진위 검증 전체를 새로 설계하지 않았다.
- 승인 시 생성되는 것은 **증명서 레코드·고정 payload·서명 요청**이다. 운영 서명은 비동기이며 완료 전 READY로 표시하지 않는다. 철회와 서명이 경합해도 최신 효력은 철회 기록을 조회해 판단해야 한다. 현재 프로토타입 QR은 여전히 서명 없는 요약이다.

## 강의 근거와 생성

PDF 읽기 스킬로 강의 자료를 확인했다. `Ch06_요구 모델링_정적-동적-final.pdf` 15쪽의 모델링 순서, 33쪽 다중성, 38쪽 클래스 작성, 44~46쪽 상호작용, 52·54쪽 상태와 61~63쪽 모델 간 일관성 검사를 적용했다. `Ch07_아키텍처-part1.pdf` 8~10쪽의 패키지 그룹·의존과 컴포넌트 인터페이스 구분을 적용했다. 기존 [프로젝트 맥락](../../project-context.md), [운영 구조](../../architecture.md)와 승인·저장 규칙을 대조했다.

수정 원본: [model.json](model.json)의 클래스·관계·조건·UC 계약, [render.cjs](render.cjs)의 각 그림 전이·배치·상호작용. `sources/`의 DOT·순서 JSON과 PNG·SVG·HTML은 생성본이다. Playwright·Chrome·`@viz-js/viz`가 필요하며, 필요하면 `DIAGRAM_NODE_MODULES`를 지정하고 저장소 루트에서 `node docs/modeling/uc06-uc10/render.cjs`를 실행한다. 다른 UML·PDF·발표 자료를 재생성하지 않는다.

검증: 순서 호출의 수신 타입·공개 연산, 6개 이미지의 화면 밖 글자 검사를 validation.json에 기록한다. 최종 그림은 글자·선·경계를 눈으로 확인했다. 제품 코드가 바뀌지 않아 제품 테스트는 새로 실행하지 않았다. 운영 권한·DB·서명 설계는 구현 및 실행 검증을 마쳤다는 의미가 아니다.
