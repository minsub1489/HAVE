## 2026-10-26 유스케이스 개요 최적화

최적화한 PNG · 확대 가능한 SVG · [수정 원본과 원본 52개 항목 대응표](optimized/use-cases.json)

프로젝트의 목적·현재 구현·운영 계획을 함께 파악하려면 [프로젝트 맥락과 작업 인수인계](../project-context.md)를 먼저 읽는다. 대응표의 근거인 [사용자 제공 원본 이미지](references/use-cases-original.png)도 저장소에 보관한다.

첨부된 52개 항목의 전체 서비스 도식과 현재 저장소 구현을 대조해, **현재 로컬 MVP는 액터 3개·사용자 목표 9개**로 표현했다. 아래 기존 모델의 UC-01~UC-08 번호를 유지하고 증명서·버전·승인 이력 조회를 UC-09로 추가했다. 이 번호는 첨부 이미지의 UC 번호와 별개이며 대응표의 `originalIds`가 이미지 번호다. 기존 상세 다이어그램과 제품 코드는 유지한다.

현재 검토자가 최종 승인도 수행하며, Chrome 확장은 HAVE 내부 구성요소다. 세 과제와 승인 조건, 특정 버전·검토 범위 고정, 새 버전 승인 미상속, 철회와 후속 버전 분리, 사용자 선택 시에만 파일 비교한다는 규칙을 유지한다. 화면 조작·검증·저장·실패 복원·서명 작업은 사용자 목표 타원을 늘리는 대신 기존 명세·시퀀스에 연결한다. 증명서는 승인 결과로 생성되며 별도 발급 요청을 새로 도입하지 않는다.

원본의 전체 서비스 요구사항을 삭제한 것은 아니다. 수정 원본의 `originalMapping`에 1~52번을 각각 한 번씩 분류했고, `plannedGoals`에 계정·권한·배정, 정책 관리, 운영·통계, 서명/현재 효력 검증, 공개 결과물·승인 지식 활용을 별도 기획 범위로 보존했다. 블록 편집, 독립 최종 승인자, 지식 검색 같은 미구현 요구를 현재 기능처럼 표시하지 않는다. 운영 계획의 서버·Outbox 작업자는 시스템 내부 책임이며, 업무 승인과 서명 영수증 준비 상태는 기존 운영 시퀀스에서 구분한다.

현재 QR은 **서명 없는 발급 당시 요약**이고 다른 기기에서 최신 효력을 확인할 수 없다. 기여 JSON은 승인 명령이 아니며, 기여 변경 후 기존 평가를 초기화하는 절차도 유지한다. 역할 전환은 실제 계정/권한 구현이 아니다. 운영 관리 묶음은 별도 뷰의 상위 분류이며 계정별 권한과 운영 세부 목표를 하나로 합친다는 뜻은 아니다.

개요만 다시 생성하려면 `DIAGRAM_NODE_MODULES`에 Playwright 패키지 경로를 지정하고 `node docs/modeling/optimized/render.cjs`를 실행한다. 렌더러는 대응표의 52개 항목 누락/중복, MVP 액터·목표 수, 화면 밖 텍스트를 확인하며 기존 갤러리/PDF를 재생성하지 않는다.

2026-10-14 기준. 강의 `Ch06_요구 모델링_정적-동적-final.pdf`의 유스케이스 → 개념 클래스 → 상호작용 → 상태/활동 → 모델 검증 순서에 따라 정리했다. 발표 PPT는 변경하지 않았다.

## 확정한 모델링 기준

- 작업에는 버전이 1개 이상 있다. 버전 번호는 작업 안에서 유일하다. 현재 시연 저장소에는 작업 하나만 저장된다.
- 승인 대상은 파일명이나 작업 전체가 아니라 **특정 버전 ID와 파일 SHA-256, AI 신고, 검토 범위**다. 파일/신고/위험도 변경은 새 버전으로 만든다. 같은 PDF라도 신고 내용이 달라지면 새 버전이 될 수 있다.
- 현재 MVP는 Teach-back, Fault Injection, What-if **세 과제 고정**이다. 위험 점수는 참고 정보이며 과제 수를 자동 변경하지 않는다. 정책 스냅샷은 버전에 고정한다.
- 세 답변 제출, 평가 근거, 합계 **5/6 이상**, 치명 오류 없음, 반려 해제, 체크 네 항목, 최종 메모, 검토자 역할, 기존 승인 없음, 저장 가능을 모두 확인한다. 자기 확신도는 통과 점수가 아니다.
- 단일 검토자 MVP에서 **버전당 승인 0..1건**이다. 철회해도 같은 버전을 다시 승인하지 않는다. 재승인은 새 버전과 새 검토로 진행한다. 복수 검토자 1:N은 확장 설계다.
- 현재 답변/평가와 이전 검토 회차를 구분한다. 수정 요청 또는 기여 근거 변경은 이전 회차를 보존하고 현재 평가·체크·메모를 초기화한다. 기여 근거 추가만으로 이미 제출한 답변이 자동 미제출되지는 않는다.
- 승인 후 답변·평가·기여·체크·메모는 변경하지 않는다. 승인 당시 검토 스냅샷의 `reviewDigest`를 유지한다. 철회는 승인 기록 삭제가 아니라 별도 시각/사유다.
- **검토 완료 ≠ 승인 완료**다. **후속 버전 존재 ≠ 승인 철회**다. 검토 진행, 승인 효력, 버전 관계를 각각 모델링한다. 현재 UI는 이 차원을 우선순위로 한 배지에 요약한다.
- 승인·감사 기록은 저장 성공 이후 표시한다. 저장 실패 시 복원하고, revision 충돌 시 최신 기록 확인을 요구한다. 자동으로 다시 승인하지 않는다.
- 현재 QR은 **서명 없는 발급 당시 요약**이다. 해당 기록을 가진 브라우저만 로컬의 현재 철회/후속 버전을 확인한다. 다른 기기는 최신 효력을 확인할 수 없다. 파일 선택 전에는 파일 일치 여부도 미확인이다.
- 해시는 바이트 동일성을 확인한다. 이해 과제는 검토 판단의 근거를 남긴다. 둘 다 문서의 사실 정확성, 실제 이해, AI 신고의 진실성을 보증하지 않는다.
- 현재 역할 전환은 계정 인증이 아니다. 실제 계정과 작업별 역할은 운영 설계다. 한 사람이 작업마다 다른 역할을 가질 수 있어 작성자/검토자를 User의 상속 클래스로 만들지 않는다.

## 클래스 관계 해설

핵심 모델은 `Work → Version → Approval → Receipt`와 버전의 `Contribution`, `RiskAssessment`, `ReviewPolicy`, `AuditEvent` 연결을 보여 준다. `Receipt`는 개념적으로 분리했지만 현재 코드에서는 payload/digest가 승인 객체에 포함된다. 운영 모델에서는 승인 직후 서명 영수증이 아직 없을 수 있어 `Approval → Receipt`를 0..1로 둔다. 서명 완료 후에는 한 승인에 같은 ID의 영수증 한 건만 준비한다.

검토 모델의 `GateResponse`는 한 과제의 현재 답변 슬롯이며 빈 초안도 존재한다. 과제당 현재 평가가 0..1건 있다. 과거 `ReviewRound`는 당시 세 슬롯과 체크·메모의 스냅샷이며 현재 평가와 별개다. 현재 구현의 필드 구조를 읽기 쉬운 개념으로 분해한 것으로, 과제·답변·평가가 모두 별도 DB 테이블로 구현되었다는 뜻은 아니다. 실제 `Version.gates[]`가 답변과 평가를 함께 담는다.

모든 관계는 기본 연관으로 표현했다. 작업 삭제, 개인정보 삭제, 감사 보존 기간이 아직 결정되지 않아 UML 합성의 강한 삭제 의미를 임의로 부여하지 않았다. 클래스의 `submit/evaluate/revoke` 등은 **개념 책임**이며, 실제 메서드 명세는 구현 시퀀스와 코드 연결표를 따른다.

UC-07의 파일 비교는 사용자가 파일을 선택할 때 실행되는 선택적 행동이다. 따라서 QR 열기의 필수 `include`로 만들지 않았다. 반면 UC-04의 승인 조건 확인은 승인 실행의 필수 `include`다. Chrome 확장은 HAVE의 일부로 포함되므로 외부 사람처럼 액터로 그리지 않았다. 외부 웹 페이지는 근거 입력으로 구성도에 표시한다. 자동 AI 채점 API가 없으므로 AI를 독립 액터로 추가하지 않았다.

검증 시 ① 유스케이스의 참여자가 시퀀스에 등장하는지, ② 메시지가 실제 함수 또는 계획 책임에 연결되는지, ③ 상태 전이의 guard가 승인 규칙과 같은지, ④ 0..1 승인 제약과 새 버전 미상속이 모든 그림에서 같은지, ⑤ 실패 경로에서 성공 상태가 남지 않는지를 확인한다. 시퀀스의 `alt`는 상호 배타 분기, `opt`는 선택 조건이다. UI 이벤트의 직렬화는 실제 `transaction()`에 반영했으며 비동기 함수라는 이유만으로 병렬 `par`를 쓰지 않았다.

활동 그림의 빈 마름모는 택일 흐름의 합류(merge)다. 최초 입력과 재작업이 같은 활동으로 돌아갈 때 두 경로를 모두 기다리는 동기화로 해석하지 않도록 합류를 표시했다. 역할별 스윔레인은 책임을 구분하며 병렬 실행을 뜻하지 않는다. 이 그림은 주요 업무 경로이고, 손상 QR·입력 오류·저장소 초기화/복구 같은 세부 예외는 명세와 해당 시퀀스를 함께 본다.

## 운영 전에 결정할 정책

그림 11~12는 모듈형 단일 서버를 권장하는 설계이며 구현 완료 표시가 아니다.

- 작업별 작성자/검토자 배정, 자기 승인 금지, 철회 권한과 대상 승인 선택을 서버에서 검사한다. 현재 UI의 최근 승인 선택 제약은 운영 API의 명시적 `approvalId` 선택으로 개선한다.
- 승인 요청은 expected revision과 idempotency key를 사용한다. 같은 키·같은 요청은 같은 결과, 같은 키·다른 요청은 충돌이다. 최종 승인 직전에 변경 여부와 모든 조건을 다시 확인한다.
- 업무 승인·감사·outbox를 한 DB 트랜잭션에 저장한다. 서명 실패는 업무 승인을 되돌렸다고 표시하지 않는다. 서명 상태 PENDING/READY/FAILED를 별도 관리하고 같은 receipt ID/payload로 재시도한다.
- 서버가 전체 파일 바이트를 해시한다. 업로드는 STAGED → READY/FAILED/EXPIRED로 관리하고 비공개 객체 저장소, PDF 구조/악성 파일 검사, 실패한 임시 객체 청소를 추가한다.
- 공개 조회에는 공개 필드만 제공한다. 서명 검증, 조회 시각, 현재 철회, 후속 버전, 파일 비교를 구분한다. 네트워크 오류는 ‘유효’가 아니라 ‘현재 상태 확인 불가’다. 캐시·철회 반영 정책을 정한다.
- 서명키 보관/교체/유출 처리, 데이터 보존·개인정보 삭제, 백업·복구, 조회 제한, 모니터링은 별도 운영 명세가 필요하다. 감사 해시 체인만으로 끝부분 삭제나 전체 재작성까지 증명하지 않는다.
- 동적 과제 배정, Human Edit, 복수 승인자, 자동 AI 평가, 확장 API 업로드는 추가 모델링 후 구현한다. 이번 그림의 MVP와 섞지 않는다.

## 근거와 편집 방법

강의: 요구 모델링 p4~16, 클래스·다중성 p18~40, 상호작용 p43~50, 상태 p51~54, 활동 p56~58, 일관성 검증 p60~63. 함께 대조한 자료는 원래 7쪽 구현 설계서, 최종 제출 PPT, `docs/architecture.md`, 웹과 실제 확장 소스다. 설계서의 위험별 과제/버전당 복수 승인 예시는 현재 단일 검토자 MVP에 맞게 정리했다. ROI·가격·개발비는 도메인 객체로 넣지 않았다.

`sources/*.json`이 각 그림의 수정 원본이다. 구조 그림은 노드·관계·배치, 시퀀스는 참여자·메시지·분기를 보관한다. 시퀀스와 같은 이름의 `.mmd`는 Mermaid 열람용으로 생성한다. `catalog.json`에 제목·범위·설명을 보관한다. 생성된 SVG/PNG는 직접 수정하지 말고 원본에서 재생성한다. 총 13개 그림이며 PDF는 안내 1쪽을 포함해 14쪽이다.

```sh
# Node: playwright 필요. 설치된 Chrome을 사용한다.
node docs/modeling/render.cjs
# Python: reportlab, pillow 필요. Windows 기본 폰트는 맑은 고딕.
python docs/modeling/export_pdf.py
```

다른 환경에서는 `DIAGRAM_NODE_MODULES`(Node 패키지 경로), `CHROME_EXECUTABLE`(Chrome 경로), `HAVE_FONT`(한국어 TrueType 폰트 경로)를 지정한다. 렌더러는 이 문서 폴더의 산출물만 생성한다. 원본 PPT와 제품 코드는 변경하지 않는다.

새 9개 유스케이스 기반 모델만 생성할 때는 `node docs/modeling/optimized/uml/render.cjs`, PDF는 `python docs/modeling/optimized/uml/export_pdf.py`를 사용한다. 원본 `model.json`과 생성본을 구분하며 기존 갤러리를 일괄 재생성할 필요가 없다.
