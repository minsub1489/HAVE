# 상태 다이어그램과 연관 다중도 검토

## 1. 범위 확정

단일 Version의 검토·승인 절차를 주 모델로 선택했다. 기준 객체는 Version이며 미승인 영역의 Review를 하위 상태로 확장한다. 작업 전체·버전 전체·승인 효력을 하나의 status enum으로 합치지 않는다.

승인 이후에는 별도 Approval의 효력 변경 절차를 그린다. 다른 기기의 최신 효력·전자서명·삭제/보존 타임아웃은 현재 구현에 추가하지 않는다.

## 2. 시작·종료 상태

- 시작: UC-01/05의 첫 버전 저장 성공 후 빈 답변 슬롯 3개·미승인 검토
- 종료: UC-04 승인·증명·감사 commit 성공으로 해당 버전 검토·승인 절차 종료
- 종료가 아닌 상태/사건: 평가 통과, 반려/수정 요청, 저장 실패, 후속 버전 생성
- 종료 기호의 뜻: UML 최종 노드는 해당 상태기계의 실행 종료를 뜻하며 객체/저장 데이터 삭제를 뜻하지 않는다.

최종 노드는 검토·승인 절차 또는 승인 효력 변경 절차의 종료다. 객체의 삭제나 더 이상 조회할 수 없음을 뜻하지 않는다. ST01의 승인 종료 후에도 ST02의 철회가 가능하다. 철회 후 같은 버전의 재승인·철회 취소는 불가능하다.

## 3. 상태와 하위 상태

| 영역 | 상태 | 의미 |
| --- | --- | --- |
| Version 미승인 검토 | 답변 작성 중 | 미제출 답변 존재, 치명 오류·returned가 우선하지 않는 경우 |
| Version 미승인 검토 | 검토 대기 | 세 답변 제출됨, 평가 통과 조건 미달 |
| Version 미승인 검토 | 평가 통과 | 과제 조건 통과. 체크·메모 등을 포함한 최종 승인 조건과 별개 |
| Version 미승인 검토 | 수정 요청 | returned 또는 현재 평가의 치명 오류 |
| Version 절차 종료 전 | 승인 완료 | 승인·증명·감사 저장 성공, 검토 범위 고정 |
| Approval 효력 | 미철회 승인 / 승인 철회 | 단방향 효력 변경. 후속 버전 존재와 별개 |

판정 우선순위: K 또는 R → 수정 요청; 그 외 P → 평가 통과; 그 외 S → 검토 대기; 나머지 → 답변 작성 중

입력 슬롯 생성은 UC-01/05에서 한 번 수행한다. 답변 작성 중으로 재진입할 때마다 Review·GateResponse를 새로 생성하는 entry 액션을 넣지 않았다. 상태가 유지되는 부분 제출·체크 보완·조회는 새 객체 수를 늘리지 않는다.

## 4. 이벤트·조건·액션

화살표는 `이벤트 [조건] / 액션`으로 읽는다. 그림의 T 번호를 아래 행과 연결한다. 모든 호출에 역할/대상/입력 검증과 저장 성공이라는 공통 전제가 있다.

- **S**: 세 답변 모두 제출
- **R**: 수정 요청 플래그 returned
- **K**: 현재 평가 중 치명 오류 존재
- **P**: gatesPassed: S·평가 근거·정수 0..2점·5/6 이상·!R·!K
- **A**: P·체크 4개·메모·검토자 역할·기존 승인 없음·저장 가능·revision 일치·commit 성공

| ID | 출발 → 도착 | 이벤트 | 조건 | 액션 |
| --- | --- | --- | --- | --- |
| T01 | 작성 중 → 검토 대기 | Review.submit | S && !K | 답변·확신도 저장, 마지막 제출 시 R 해제 |
| T02 | 검토 대기 → 평가 통과 | Review.evaluate | P | 현재 평가 기록 |
| T03 | 검토 대기 → 수정 요청 | Review.requestRevision | S && 미승인 && 사유 있음 | 회차 +1, 제출·평가·체크·메모 초기화, R=true |
| T04 | 검토 대기 → 수정 요청 | Review.evaluate | K | 치명 오류 평가 기록 |
| T05 | 평가 통과 → 수정 요청 | Review.requestRevision | 미승인 && 사유 있음 | 회차 +1, 제출·평가·체크·메모 초기화, R=true |
| T06 | 평가 통과 → 수정 요청 | Review.evaluate | K | 치명 오류 평가 기록 |
| T07 | 평가 통과 → 검토 대기 | Review.evaluate | S && !R && !K && !P | 현재 평가·근거 변경 |
| T08 | 평가 통과 → 검토 대기 | Version.attachContributions | 신규 근거 && 미승인 | 회차 +1, 평가·체크·메모 초기화, 제출 유지 |
| T09 | 수정 요청 → 검토 대기 | Review.submit | S && !K | 재제출 완료 시 R 해제 |
| T10 | 수정 요청 → 검토 대기 | Review.evaluate | S && !R && !K && !P | 치명 오류 해제 후 미통과 평가 |
| T11 | 수정 요청 → 평가 통과 | Review.evaluate | P | 치명 오류 해제 후 통과 평가 |
| T12 | 수정 요청 → 작성 중 | Review.evaluate | !S && !R && !K | 부분 제출 답변의 치명 오류 해제 |
| T13 | 작성 중 → 수정 요청 | Review.evaluate | K && 대상 답변 제출됨 | 부분 제출 상태에서도 가능한 치명 오류 평가 |
| T14 | 미승인 복합 상태 → 승인 완료·절차 종료 | Version.approve | A | 승인 1건·증명 1건·감사 생성, 검토 범위 고정 |
| T15 | 모든 미승인 하위 상태 → R/S로 재판정 | Version.attachContributions | 신규 근거 && 입력·상한 유효 | 회차 +1, 평가·체크·메모 초기화; R/제출은 유지 |

T15의 재판정: 기여 추가는 현재 평가를 모두 지우므로 P는 거짓이다. returned가 남아 있으면 수정 요청, returned가 없고 세 답변이 제출되어 있으면 검토 대기, 나머지는 답변 작성 중이다. 기존 제출 여부와 returned를 임의로 초기화하지 않는다. 그림의 T12/T15 화살표는 실제 도착이 작성 중인 경우만 뜻한다.

자기 전이: 부분 제출, 현재 평가/근거 보완, 체크·메모 변경, returned가 유지되는 기여 연결 등은 판정 결과가 같으면 같은 상태다. 수정 요청 상태에서 세 답변이 제출되어 있고 사유가 있으면 다시 수정 요청할 수도 있으며, 회차만 추가되고 상태는 유지된다.

거부: 미제출 답변 평가, 승인된 범위 변경, 사유 없는 수정/철회, 중복 승인, 모두 중복인 기여, 상한 초과 등은 성공 전이가 아니다. 실패 시 전이 취소. 충돌 시 이전 요청 성공으로 표시하지 않고 최신 상태를 검증·조회한다.

후속 버전 생성은 새로운 상태기계 인스턴스의 시작이다. 이전 버전의 검토나 승인을 초기 상태로 되돌리는 전이를 그리지 않는다.

## 5. 다중도 감사와 유스케이스 반영

관계 `A "m" -- "n" B`에서 A 하나가 참조하는 B 수는 n, B 하나가 참조하는 A 수는 m이다. 아래 표는 양쪽 끝을 함께 확인한다. `*`는 구조적 다중도이며 현재 스키마의 개수 상한은 별도 제약으로 적는다.

| ID | 연관 | 판정 | 성립 조건·범위 | 관련 UC |
| --- | --- | --- | --- | --- |
| R01 | Work `1` -- `1..*` Version | 유지 | 작업은 첫 버전 저장 성공 후 존재. 현재 스키마는 버전 1~10000개. | UC-01, UC-05 |
| R02 | Version `1` -- `1` Review | 유지·조건 명시 | 버전마다 현재 검토 1개. 재제출·수정 요청은 현재 검토 수를 늘리지 않음. | UC-01, UC-02, UC-03, UC-05, UC-08 |
| R03 | Review `1` -- `3` GateResponse | 유지 | 빈 초안 포함 고정 슬롯 3개. 답변 회수·재제출로 슬롯을 추가/삭제하지 않음. | UC-01, UC-02, UC-03 |
| R04 | GateResponse `1` -- `0..1` Evaluation | 유지·범위 명시 | 답변 슬롯의 현재 평가만 0..1개. 이전 회차의 평가는 스냅샷 값으로 별도 보존. | UC-02, UC-03, UC-08 |
| R05 | Review `1` -- `0..*` ReviewRound | 유지·상한 명시 | 수정 요청·신규 근거 연결 성공마다 과거 회차 1개. 스키마 상한 1000개. | UC-03, UC-08 |
| R06 | Version `1` -- `0..*` Contribution | 식별 범위 보완 | 버전별 사본의 개념 키는 (versionId,recordId). 버전 내 중복 금지·최대 100개, 버전 간 원본 ID 재사용 가능. | UC-08, UC-05 |
| R07 | Version `1` -- `0..1` Approval | 유지 | 승인 전 0건, 승인 저장 성공 후 1건. 철회해도 삭제하거나 같은 버전을 재승인하지 않음. | UC-04, UC-05, UC-06 |
| R08 | Approval `1` -- `1` Receipt | 유지·범위 명시 | 현재 로컬 모델: 승인과 payload를 같은 저장에 생성. 재다운로드는 새 증명이 아님. 운영 비동기 서명은 별도 0..1 설계. | UC-04, UC-09 |
| R09 | Work `1` -- `0..*` AuditEvent | 유지 | 사건은 작업에 속하며 삭제/재작성하지 않음. 사건 대상 버전은 같은 작업 안에 존재해야 함. | UC-01, UC-03, UC-04, UC-05, UC-06, UC-08 |
| R10 | Version `1` -- `0..*` AuditEvent | 누락 연관 추가 | 감사 사건은 정확히 대상 버전 1개를 가리킴. 단순히 Work 소속만 그리면 이 제약이 사라짐. | UC-01, UC-03, UC-04, UC-05, UC-06, UC-08 |

수정한 구조: Version–AuditEvent 연관을 추가했다. 기존 Work–AuditEvent 연관은 작업 소속을 나타내므로 함께 유지한다. 사건의 대상 버전은 그 작업 안에 있어야 한다.

보완한 해석: Contribution은 전역 원본 기록이 아니라 버전별 사본/연결 값이다. `/key=(versionId,recordId)`는 소속 버전에서 유도하는 개념 식별자이며 실제 JSON에 새 versionId 필드를 요구한 것이 아니다. 같은 ID를 다른 버전에 가져오는 것은 허용하지만 같은 버전에서 중복 추가는 거부한다.

ReviewRound는 과거 값 스냅샷이고 Evaluation은 현재 슬롯의 평가다. 여러 회차가 존재해도 현재 평가가 답변 하나에 여러 개 붙는 것이 아니다. 원본 기록과 사본을 전역 엔터티로 관리하려는 후속 요구가 생기면 연결 클래스를 별도 설계한다.

Approval–Receipt 1:1은 현재 로컬 저장의 payload 모델이다. 운영 서비스에서 승인 결정 후 비동기 서명 영수증이 준비되기 전 0..1인 설계는 다른 범위이며 섞지 않는다.

## 6. 강의 근거와 검증

보조 PDF 11쪽의 상태/이벤트/액션, 12~13쪽의 가드와 종료 예, 14쪽의 복합 상태, 15쪽의 독립 병행 영역, 16쪽의 다섯 작성 단계를 적용했다. 사례의 재승인·기간 경과 종료는 HAVE의 요구로 복사하지 않았다. 현재 예제는 인과적으로 이어지는 단계이므로 임의의 병렬 지역을 추가하지 않았다.

코드 근거: `prototype/dist/domain.js`의 `validateDatabase`, `gatesPassed`, `status`, `validateTransition`; `app.js`의 `confirmContributions`, `returnForm`, `approve`, `revokeForm`, `transaction`.

재생성: `python docs/modeling/optimized/uml/export_contracts.py`. 모델 감사: `node docs/modeling/optimized/uml/audit_constraints.cjs`. 현재 4개 관련 그림만 생성: `node docs/modeling/optimized/uml/render.cjs C01-domain C02-review ST01-lifecycles ST02-approval`.
