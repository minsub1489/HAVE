# HAVE 운영 MVP 아키텍처 패턴

**설계 결정 · 2026-11-04 · UC01~UC10**

패키지 번호와 책임은 [확정 서버 서브시스템 8개](subsystem-decision.md)를 따른다.

새 운영 요구나 검증 결과로 이 결정의 전제가 달라지면, 후보 구조와 기존 사용자 계약에 미치는 영향을 비교해 결정을 갱신한다. [요구사항에서 시작하는 아키텍처 설계](architecture.md#요구사항에서-시작하는-아키텍처-설계)

HAVE의 운영 MVP는 **모듈형 모놀리스(Modular Monolith)**, **포트와 어댑터(Ports and Adapters)**, **트랜잭셔널 아웃박스(Transactional Outbox)**를 사용하도록 설계했다. [운영 설계](architecture.md)

| 결정 수준 | 패턴 | HAVE에서 맡는 역할 |
| --- | --- | --- |
| 배포와 업무 경계 | 모듈형 모놀리스 | 하나의 API와 업무 DB 안에서 버전·검토·승인의 일관성을 유지한다. |
| 코드 의존 방향 | 포트와 어댑터 | 응용 서비스가 저장소·파일·알림 계약을 사용하고, 인프라 어댑터가 그 계약을 구현한다. |
| 비동기 작업의 신뢰성 | 트랜잭셔널 아웃박스 | 승인과 서명 요청을 함께 기록하고, 서명 작업자가 일시적인 실패를 재시도한다. |

## 패턴 선택 근거

| 후보 | 적용 판단 |
| --- | --- |
| 모듈형 모놀리스 | 채택. 검토한 버전과 승인 대상이 일치하는지 검사하고 승인·감사·서명 요청을 같은 DB 트랜잭션에서 확정할 수 있다. 팀이 관리할 배포와 운영 경계도 단순하다. |
| 전통적인 계층형 구조 | 화면·응용·도메인의 책임 분리에 활용한다. 저장 기술을 교체하거나 업무 규칙을 테스트할 수 있도록 외부 연동은 포트로 분리한다. |
| 마이크로서비스 | 재평가 후보. 업무 API를 나누면 버전·검토·승인 사이의 원자적 검사와 기록에 추가 조정이 필요하다. 모듈별 독립 배포나 부하 격리가 실제로 필요해질 때 검토한다. |

## 모듈과 의존 규칙

화면·API는 응용 서비스를 호출한다. 응용 서비스는 유스케이스와 트랜잭션을 조정하고, 도메인은 승인 조건과 상태 전이를 판단한다. 인프라 어댑터는 응용 계층이 정의한 포트를 구현한다. 모듈은 공개된 응용 계약으로 협력하고 각 업무 데이터의 변경은 소유 모듈이 담당한다. 공유 DB에서도 이 변경 권한을 유지한다. 읽기 모듈은 버전·검토·승인·감사를 조합한 조회 결과를 제공한다.

업무 API를 초기 운영 배포 단위로 둔다. 서명 작업자는 같은 시스템의 비동기 실행 단위로 두고 별도 프로세스로 실행하는 것을 기본 설계로 삼는다. 업무 DB, 비공개 파일 저장소, 서명키 관리는 외부 자원 경계로 둔다.

## 레벨별 패키지와 제공·요구 인터페이스

레벨 2는 서브시스템 사이의 의존을, 레벨 3은 서브시스템 내부의 응용·도메인 패키지와 타입 소속을 보여준다. 과제의 상세 레벨 기준이 별도로 제공되기 전까지 이 구분을 HAVE 설계 기준으로 사용한다. 6강의 추상화·서브시스템 식별, 7강 Part 1의 패키지·인터페이스 표현, 7강 Part 2의 설계 패턴과 시나리오 평가를 적용했다.

각 모듈은 다른 모듈에 버전 ID·revision·정책 버전·검토 해시처럼 계약에 필요한 값을 넘긴다. UC05가 최종 반려를 근거로 재제출할 때는 응용 계층에서 Approval의 반려 사실을 확인해 재검토 흐름에 넘긴다. 근거의 대상 버전과 현재 revision은 등록 트랜잭션에서 확인한다. 패키지 그림은 [서버 서브시스템 결정](subsystem-decision.md), 타입과 다중도는 [통합 클래스 모델](modeling/integrated/README.md)에서 확인한다.

## 내부 설계 패턴

파일 저장 어댑터는 `FileStore` 계약을 비공개 저장소의 SDK 호출로 변환한다. 전략 패턴은 검토 정책에 따라 평가 알고리즘을 바꿀 때 `GatePolicy`의 구현을 나누는 데 쓸 수 있다. 검토 기록에는 적용된 정책 버전과 결과를 함께 보존한다. [클래스와 패턴별 설계도](modeling/integrated/class-views/index.html)

변경 시나리오로 파일 저장 공급자 교체를 검토했다. 같은 `FileStore` 계약을 충족하면 영향 범위는 어댑터, 연결 설정, 연동 확인이다. 새 공급자의 임시 파일 정리나 접근 제한 방식이 다르면 그 차이도 어댑터에서 처리하고, 확정된 버전과 파일 해시가 같은지 확인한다. 아래 장애 시나리오와 함께 구현 검증의 기준으로 사용한다.

## 승인과 서명 사이의 트랜잭션 경계

1. API가 세션과 작업별 권한을 확인한다. 승인 서비스는 트랜잭션 안에서 버전·검토 revision, 자기 승인 금지, 승인 조건, 기존 승인 여부를 다시 검사한다.
2. 승인 기록, 증명서의 고정 payload와 `PENDING` 상태, 감사 이벤트, Outbox 이벤트를 한 번에 커밋한다. 버전당 승인 한 건은 DB 유일 제약으로 보장한다. 같은 멱등 키와 같은 요청은 기존 처리 결과를 반환하고, 같은 키로 내용이 달라지면 충돌로 처리한다.
3. 작업자가 커밋된 Outbox 이벤트를 가져와 서명한다. 중복 처리에 대비해 증명서 ID와 payload 해시를 확인하고, 서명 결과와 이벤트 처리 완료를 함께 기록한다. 작업 중 중단된 이벤트는 다시 가져올 수 있게 하고, 일시적인 실패는 동일 증명서와 payload로 재시도한다. 재시도 한도를 넘기면 `FAILED`와 실패 원인을 기록해 운영자가 확인한다.
4. 철회는 권한과 현재 효력을 확인한 뒤 철회 기록과 감사를 함께 커밋한다. 서명 작업자가 나중에 완료되더라도 바뀌는 값은 서명 준비 상태다. 공개 검증은 조회 시점의 철회 기록을 기준으로 현재 효력을 표시한다.

| 확인할 상황 | 기대 동작 |
| --- | --- |
| 같은 버전의 승인 요청이 동시에 도착 | 승인 한 건만 확정되고 나머지 요청은 멱등 결과 또는 충돌 응답을 받는다. |
| DB 커밋 전에 오류 발생 | 승인·감사·Outbox가 함께 롤백된다. |
| 서명은 성공했지만 결과 저장 전에 작업자 중단 | 이벤트를 다시 처리하고 같은 증명서에 결과를 기록한다. |
| 서명 대기 중 철회 | 서명 상태와 철회 상태를 각각 표시한다. 공개 조회에서 유효한 승인으로 표시하지 않는다. |
| 공개 조회에서 최신 효력을 확인할 수 없음 | 효력은 확인 불가로 표시한다. 서명 진위와 선택 파일의 해시 일치는 각각 반환한다. |
| 파일 저장 뒤 DB 등록 실패 | 미확정 파일을 정리한다. DB에서 확정된 버전만 검토 대상으로 사용한다. |

공개 검증은 증명서 식별과 공개 범위 확인을 거쳐 필요한 필드만 반환한다. 현재 효력 응답은 철회 직후 이전 결과가 재사용되지 않도록 캐시 정책을 적용한다. 공유 링크 만료, 서명 진위, 현재 효력, 후속 버전 유무, 파일 일치는 각각 조회 결과로 표현한다.

서명 처리량이 늘면 작업자부터 독립적으로 확장한다. 업무 API 분리는 모듈별 부하, 장애 영향, 배포 주기의 차이가 관측되고 데이터 소유권과 실패 복구 계약을 명확히 정의할 수 있을 때 검토한다.
