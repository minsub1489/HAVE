# HAVE UI 가이드라인

버전 0.3 · 팀 협의용 제안 · 2026-11-18 (0.2는 2026-11-11)

> 0.3 변경: 크롬 확장 프로그램 화면(측면 패널 400px · 팝업 360px) 기준 추가, 상태 키를 통합 상태 다이어그램에 맞춰 확정, 토큰 파일 이름을 실제 파일(`공통.css`)로 정정, 파일 제한과 근거 문서 경로 정정.

각자 맡은 화면을 구현해도 하나의 서비스처럼 보이고 동작하게 만드는 공통 규칙이다. 기존 HAVE 구조 설계와 세부 기능 설계를 기준으로 작성했다. 실제 프론트엔드 소스와 확정된 디자인은 이 작업 폴더에서 확인되지 않았으므로, 아래 시각 규칙과 컴포넌트 계약은 새 제안이다. 기존 기능 문서 사이의 역할·상태 차이는 백엔드 계약 확정 시 매핑한다.

## 1. 팀이 먼저 맞출 원칙

1. 색상·간격·글자 크기는 `공통.css`(v0.2)의 토큰을 공통으로 쓴다.
2. 사이드바, 페이지 헤더, 버튼, 입력창, 배지는 공통 컴포넌트를 한 번 만들고 가져다 쓴다.
3. 모든 작업 화면 상단에 **작업명 / 대상 버전 / 현재 상태 / 다음 행동**을 둔다.
4. 검토 결과, 최종 승인, 증명서 발급, 공개 검증은 각각의 결과로 표시한다.
5. 새 버전 생성 후 이전 승인 기록을 새 버전의 승인으로 표시하지 않는다.
6. 정상 화면과 함께 로딩·빈 목록·실패·권한 부족 상태도 구현한다.

시각 방향은 ‘차분하고 명확한 검토 업무 도구’다. 흰색 본문, 옅은 회색 배경, 진한 남색 글자, 청록색 주요 행동과 빨간색 보조 강조을 사용한다. 색은 상태와 행동을 찾는 용도로 제한하고 그라데이션, 유리 효과, 장식용 차트는 사용하지 않는다. 라이트 테마를 1차 범위로 제안한다.

## 2. 화면 뼈대와 반응형

| 항목 | 공통 규칙 |
| --- | --- |
| **측면 패널 (기본 화면)** | 폭 400px 고정. 사이드바 대신 상단 탭 3개(내 작업 / 검토할 작업 / 승인할 작업), 주요 행동은 패널 하단 고정 영역에 1개 |
| **팝업** | 폭 360px. 지금 할 일, 측면 패널 열기, 현재 탭 PDF 등록, 증명서 검증 진입만 담는다. 긴 입력·검토는 측면 패널에서 한다 |
| 넓은 화면 ≥1024px (전체 화면으로 열 때만) | 왼쪽 내비게이션 232px + 상단 바 64px + 본문 |
| 본문 | 최대 1200px, 가운데 정렬, 좌우 패딩 32px, 상하 32px |
| 768~1023px | 사이드바를 메뉴 버튼으로 전환, 본문 패딩 24px |
| <768px | 1열, 본문 패딩 16px, 페이지 제목 24px, 액션 버튼 필요 시 세로 배치 |
| 등록·입력 화면 | 폼 최대 720px; 긴 입력창을 전체 화면 너비로 늘리지 않음 |
| 공개 검증 | 업무 사이드바 없이 최대 800px; 모바일 QR 진입 우선 |
| 상세 화면 | 본문 + 320px 요약 영역, 간격 24px; 1024px 미만이면 세로 배치 |
| 목록 | 데스크톱은 표, 모바일은 동일 필드를 가진 카드; 중복 DOM이면 숨긴 영역은 포커스 불가 |

HAVE는 크롬 확장 프로그램이므로 업무 화면의 기준은 측면 패널이다. 아래 넓은 화면 규칙은 같은 화면을 전체 탭으로 열 때만 적용한다. 기본 내비게이션은 ‘내 작업 / 검토할 작업 / 승인할 작업’으로 제안한다. 승인할 작업은 최종 승인 역할이 분리될 때 표시한다. 증명서와 이력은 작업 상세의 하위 탭에서 찾게 하고, 공개 검증은 별도 진입점으로 둔다. 권한은 계정 전체 직함보다 **현재 작업에서의 역할**을 기준으로 판단한다. 목록 접근이 허용된 사용자가 읽기만 가능한 경우에는 액션 근처에 이유를 표시한다.

페이지 헤더 순서: 상위 경로(필요 시) → 제목·설명 → 우측 주요 행동. 헤더 아래 필터 또는 버전 요약 → 본문 순으로 고정한다. 주요 행동은 한 액션 영역에 청록색 버튼 1개만 둔다.

배경색 위 텍스트는 같은 의미의 진한 색을 쓴다. 상태는 반드시 글자로 함께 표시한다. 초록색은 서비스가 확인한 범위에만 사용하며 ‘문서 내용이 사실임’이나 ‘실제 이해가 보장됨’으로 확장해 표현하지 않는다.

### 청록 메인·빨강 서브의 사용 규칙

청록과 빨강을 서로 대비되는 브랜드 조합으로 사용한다. 가독성과 업무 집중도를 위해 채도를 조절한 딥 틸과 웜 레드를 선택했다. 모든 강조를 두 색에 같은 비중으로 배분하지 않는다.

| 구분 | 사용 위치 | 피할 사용 |
| --- | --- | --- |
| 중립색 | 전체 배경·본문·카드·기본 테두리 | 넓은 영역을 진한 브랜드색으로 채우기 |
| 청록 Primary | 로고, 주요 버튼, 현재 메뉴·탭, 링크, 포커스, 진행 중 상태 | 완료·승인 유효 여부를 색만으로 표현하기 |
| 빨강 Accent | 가이드 보기, 새 기능·업데이트 안내, 작은 브랜드 포인트 | 일반 취소·이전 버튼, 승인·통과 배지, 폼 오류 |
| 진한 빨강 Danger | 오류, 파일 불일치, 철회·삭제 확인 버튼 | 장식·일반 안내에 재사용하기 |

시각적 면적의 출발점은 **중립색 약 80% / 청록 약 15% / 빨강 약 5%**다. 엄격한 계산 규칙이 아니라 과도한 빨강을 막기 위한 방향이다. 정보의 상태를 전달하는 초록·노랑 등은 필요한 곳에 별도로 사용한다.

- 화면별 주요 행동은 청록색으로 유지한다. 빨강은 작은 보조 강조로 사용하고 주요 버튼과 같은 무게의 채움 버튼으로 경쟁시키지 않는다.
- `secondary`는 흰색 배경의 중립 보조 버튼이다. 브랜드의 ‘서브 색상’은 `accent` 토큰으로 분리한다. 모든 보조 버튼이 빨간색이 되는 것은 아니다.
- `accent` 버튼은 옅은 빨강 배경·빨강 글자·테두리 조합을 사용한다. 예: ‘가이드 보기’. 빨강을 눌러야만 다음 단계로 진행되는 핵심 흐름은 만들지 않는다.
- `danger`는 진한 빨강과 ‘승인 철회’, ‘파일 불일치’처럼 결과가 분명한 문구를 함께 사용한다. 두 빨강 계열의 구별을 명도 차이만으로 판단하게 하지 않는다.
- 공개 검증·최종 승인·오류 화면에서는 빨간 장식이나 비업무용 보조 강조를 줄여 결과와 경고를 먼저 읽게 한다.
- 성공은 기존 초록, 주의는 황갈색을 유지한다. 진행 중인 청록 배지와 완료된 초록 배지는 반드시 상태 문구를 함께 표시한다.
- 청록과 빨강의 진한 색 위에 서로의 글자를 얹지 않는다. 두 색 모두 흰색이나 각자의 옅은 배경과 조합한다.

### 글자·간격·형태

- 폰트: Pretendard → Noto Sans KR → OS 기본 sans-serif. 폰트 파일을 팀 공통으로 제공할 때 같은 파일·굵기를 사용한다. 미리보기는 설치된 폰트로 동작한다.
- 페이지 제목 28/700, 섹션 제목 20/600, 본문 16/400, 표·버튼·보조 정보 14/400~600, 캡션 12/400. 본문 줄 높이 1.6, 제목 1.35.
- 간격: 4·8·12·16·20·24·32·40·48·64px. 라벨↔입력 8, 폼 항목 24, 카드 내부 24(모바일 16), 섹션 사이 32.
- 버튼·입력 높이 44px 이상, 텍스트 영역 최소 128px. 버튼 좌우 패딩 16px, 아이콘↔텍스트 8px.
- 컨트롤 모서리 8px, 카드 12px, 상태 배지 pill. 배지는 클릭 대상과 구분한다.
- 일반 카드는 1px 테두리로 구분하고, 그림자는 메뉴·모달 등 떠 있는 요소에만 사용한다.
- 아이콘은 팀이 정한 단일 세트의 20px 크기로 통일한다. 아이콘 단독 버튼은 접근 가능한 이름과 툴팁을 제공한다.
- 전환은 120~180ms; reduced-motion 설정을 따른다. 상태 확인을 애니메이션에 의존하지 않는다.

## 4. 상태 표기 — 업무 상태와 효력을 분리

아래 표기는 통합 상태 다이어그램(1118)과 DB 코드 표의 서버 값에 1:1로 대응한다. 하나의 매핑 파일에서 서버 상태를 이 표기로 변환하고 알 수 없는 상태는 ‘상태 확인 필요’로 표시한다.

| 축 | 화면 표기 | 색·의미 |
| --- | --- | --- |
| 작업 진행 | 작성 중 / 제출 완료 | 중립 / 청록 |
| 작업 진행 | 이해 확인 대기 / 검토 대기 / 승인 대기 | 청록 + 다음 행동 설명 |
| 작업 진행 | 수정 요청 | 노랑 + 요청 내용·담당자 |
| 작업 진행 | 승인 완료 | 초록, 승인된 versionId 명시 |
| 검토 결과 | 미시작 / 진행 중 / 통과 / 보완 필요 | 중립 / 청록 / 초록 / 노랑 |
| 승인 효력 | 승인 유효 / 승인 철회 / 승인 기록 없음 | 초록 / 노랑 / 중립 |
| 최신 버전 (11-23) | 최신 버전 / 후속 버전 vN 있음 | 중립 (승인 효력과 함께 표시) |
| 증명서 발급 | 발급 중 / 발급 완료 / 발급 실패 | 청록 / 초록 / 빨강 + 재시도 |
| 파일 비교 | 파일 일치 / 파일 불일치 / 파일 미확인 | 초록 / 빨강 / 노랑 |
| 서명 검증 | 정상 / 검증 실패 / 확인 불가 | 초록 / 빨강 / 중립 |

서버 값과 화면 표기 (1118 확정):

| 서버 값 (WorkVersion.status) | 화면 표기 |
| --- | --- |
| `DRAFT` | 작성 중 |
| `SUBMITTED` | 제출 완료 |
| `CHALLENGE_PENDING` | 이해 확인 대기 |
| `REVIEW_PENDING` | 검토 대기 |
| `IN_REVIEW` | 검토 중 |
| `REVISION_REQUIRED` | 수정 요청 |
| `APPROVAL_PENDING` | 승인 대기 |
| `APPROVED` | 승인 완료 |

승인 철회는 작업 상태가 아니라 승인 효력(`VALID` 승인 유효 / `REVOKED` 승인 철회)으로 표시한다. 승인 효력은 저장하지 않고 철회 기록으로 계산한다. 후속 버전이 있는지는 승인 효력이 아니라 최신 버전 여부(최신 버전 / 후속 버전 vN 있음)로 따로 표시한다. 철회와 후속 버전은 동시에 성립하므로 하나로 합치지 않는다(11-23 수정, 이전 판의 `PREVIOUS` 이전 버전 승인은 쓰지 않는다). 증명서 발급은 `PENDING` 발급 중 / `READY` 발급 완료 / `FAILED` 발급 실패, 검증 결과는 서명 `PASS`·`FAIL`·`UNKNOWN`, 파일 `MATCH`·`DIFFERENT`·`NOT_CHECKED`를 각각 정상·검증 실패·확인 불가, 파일 일치·파일 불일치·파일 미확인으로 표기한다.

예: v1 승인 후 v2 등록 → 상단 ‘v2 · 검토 대기’, 버전 이력 ‘v1 · 후속 버전 v2 있음’. v1 증명서에서는 ‘v1 승인 기록’과 ‘최신 버전 v2 존재’를 각각 표시한다. v1이 철회됐다면 공개 검증에 ‘v1 승인 철회 · 후속 버전 v2 있음 · 선택 파일은 v1과 일치’처럼 함께 보인다. v1의 효력 판정은 서버 결과를 따른다(브라우저 로컬 시연에서는 그 브라우저의 기록으로 판정).

검증 화면은 **승인 효력 / 서명 검증 / 파일 비교** 세 행을 사용한다. 파일을 올리지 않으면 ‘파일 미확인’이다. 네트워크 오류는 ‘확인 불가’이며 불일치나 철회로 바꾸지 않는다. ‘검증됨’ 배지 하나로 전체 결과를 뭉치지 않는다.

## 5. 공통 컴포넌트 계약

프레임워크와 무관한 최소 계약이다. 아래 이름을 공통 컴포넌트명으로 권장한다.

| 컴포넌트 | 공통 입력·변형 | 행동 규칙 |
| --- | --- | --- |
| AppShell | activeNav, children | 공통 내비게이션·너비·모바일 메뉴, 본문 바로가기 |

버튼 문구는 ‘확인’ 대신 ‘검토 요청’, ‘답변 제출’, ‘최종 승인’, ‘새 버전 등록’, ‘링크 복사’를 쓴다. 작성 중 저장과 확정 제출을 구분한다. 복사 완료는 짧은 알림으로, 승인·철회 결과는 화면에도 남긴다.

최종 승인 버튼이 비활성이면 아래에 ‘체크리스트 2개를 완료하면 승인할 수 있어요’ 같은 사유를 항상 표시한다. tooltip에만 숨기지 않는다. 서버에서 조건이 바뀌면 최신 상태를 다시 받아 안내한다. UI의 비활성 처리는 서버 권한 검사를 대체하지 않는다.

## 7. 입력·오류·상호작용

- 파일 제한은 PDF·20MB다(프로젝트 계획서 14쪽, UC02). 값은 한 곳(`FILE_RULE`)에서 관리하고 화면별로 다른 제한을 하드코딩하지 않는다.
- 잘못된 파일: ‘PDF 파일만 등록할 수 있어요. 파일 형식을 확인해 주세요.’ 크기 초과는 실제 상한을 함께 안내한다.
- 폼 제출 실패: 상단 오류 요약과 해당 필드 아래 오류를 함께 표시하고 첫 오류로 이동한다. 필수 표시는 글자 ‘필수’를 쓴다.
- 저장 성공: 서버 응답 후 ‘저장됨 · 14:32’ 표시. 자동 저장이 없으면 ‘임시 저장’ 버튼만 두며 저장됐다고 표시하지 않는다.
- 새 버전 충돌: ‘새 버전이 등록됐어요. 변경 내용을 확인한 뒤 다시 진행해 주세요.’ 미저장 내용은 유지한다.
- 승인: 확인 모달에 작업명, 버전, 승인 후 효과를 보여 준다. 승인 성공과 증명서 발급 성공을 별도로 처리한다.
- 철회: 빨간 확인 버튼, 대상 승인·버전과 영향, 사유 입력, 취소를 제공한다. 완료 후 철회 상태와 기록이 남는다.
- 모달은 확인·짧은 입력에 사용한다. 긴 검토나 답변은 페이지에서 수행한다.
- 페이지 전환 시 미저장 내용이 있으면 이탈 확인을 제공한다. 저장·제출 중 상태는 스크린리더에도 알린다.
- ‘알 수 없는 오류’ 대신 할 수 있는 다음 행동을 쓴다. 오류 상세나 내부 스택은 제품 화면에 노출하지 않는다.

| 상태 | 공통 UI |
| --- | --- |
| 초기 로딩 | 실제 구조에 가까운 skeleton + ‘작업을 불러오는 중’ 접근성 안내 |
| 최초 빈 목록 | ‘아직 등록한 작업이 없어요’ + ‘작업 등록’ |
| 검색 결과 없음 | ‘조건에 맞는 작업이 없어요’ + ‘필터 초기화’ |
| 요청 실패 | 화면 내 안내 + ‘다시 시도’; 기존 데이터가 있으면 보존하고 갱신 실패 표시 |
| 권한 부족 | 접근 가능한 경우 읽기 전용 + 사유; 접근 불가 문서는 내용 노출 없이 안내 |
| 세션 만료 | 로그인 안내, 가능한 범위에서 미저장 입력 복구 |
| 부분 실패 | 예: ‘승인은 완료됐지만 증명서 발급에 실패했어요’ + 발급 재시도 |

## 8. 접근성·문구 기준

- 구현 목표: 일반 텍스트 대비 4.5:1 이상, 큰 글자 및 의미 있는 UI 경계·포커스 3:1 이상. 선택 팔레트만으로 준수를 단정하지 않고 실제 조합을 검사한다.
- 키보드로 모든 행동을 수행할 수 있어야 한다. 포커스를 숨기지 않고, 모바일 메뉴·모달은 포커스 이동·가두기·복귀를 처리한다.
- 입력창에는 visible label, 오류는 aria-describedby, 잘못된 입력은 aria-invalid를 연결한다. 링크와 버튼을 의미에 맞게 사용한다.
- 데스크톱 표는 table·th 구조, 모바일 카드는 제목과 필드명을 유지한다. 표의 정렬 버튼은 방향도 읽히게 한다.
- 버튼·아이콘 버튼 터치 영역 44×44px 이상, 200% 확대와 360px 화면에서 정보·행동 누락 없이 확인한다.
- 탭을 사용하면 tablist·tab·tabpanel 의미와 방향키 이동을 함께 구현한다. 단순 페이지 이동이면 링크를 쓴다.
- 제목·버튼은 짧은 명사/동사, 안내는 ‘~해 주세요/~할 수 있어요’로 통일한다. ‘에러’, ‘성공!’ 대신 구체적 결과를 쓴다.
- 날짜는 `2026.11.11 14:32 KST`처럼 표시한다. 상대 시간만 쓰지 않는다. 공개 검증의 확인 시각도 시간대를 포함한다.
- 해시는 짧게 줄여 표시할 수 있지만 전체 복사와 전체 값 확인 방법을 제공한다.

## 9. 분업·통합 규칙

화면 분담 전에 공통 UI 담당을 한 명 정하고 토큰·AppShell·Button·FormField·StatusBadge·VersionSummary를 먼저 만든다. 나머지 담당자는 동일한 기본 화면을 가져와 기능을 붙인다. 공통 UI 변경은 담당자와 합의해 원본에 반영한다.

| 담당 영역 예시 | 맡을 화면 | 공통 연동 기준 |
| --- | --- | --- |
| 공통 UI | 토큰·셸·기본 컴포넌트 | 문구·상태 매핑과 반응형 규칙 관리 |
| 작업 | 목록·등록·상세·버전 | workId/versionId와 VersionSummary |
| 검토 | 위험 분석·이해 확인·검토 | 과제·평가·차단 사유 계약 |
| 승인·검증 | 최종 승인·증명서·공개 검증·이력 | 승인 효력·서명·파일 비교 분리 |

인원에 따라 영역을 합쳐 맡는다. 화면마다 아래 항목을 공유한 뒤 구현한다.

```
화면명 / 경로 / 대상 사용자·작업 역할
주요 데이터와 대상 versionId
주요 행동 1개 / 서버 호출 / 성공 후 화면
로딩 / 빈 상태 / 오류 / 권한 부족 / 버전 충돌
사용할 공통 컴포넌트 / API 미확정 항목
```

변경 규칙: 새 색·새 버튼·새 상태가 필요하면 공통 토큰/컴포넌트/매핑에 먼저 추가한다. 담당 화면에 비슷한 사본을 만들지 않는다. 토큰은 `공통.css`를 원본으로 한다. 새 라이브러리 도입과 패키지 버전은 실제 구현 저장소에서 결정한다.

통합 전 확인 목록:

- [ ] 공통 셸, 제목 위치, 글자·색·간격 규칙을 사용했다.
- [ ] 작업명·버전·상태·다음 행동이 일관된다.
- [ ] 검토 통과와 최종 승인, 발급 성공을 혼동하지 않는다.
- [ ] v1 승인 → v2 등록 → 재검토 흐름에서 이전 승인 기록이 보존된다.
- [ ] 파일 미제공·일치·불일치·검사 실패, 승인 철회를 구분한다.
- [ ] 로딩·빈 목록·실패·권한·중복 제출·충돌을 처리한다.
- [ ] 1440px·1024px·768px·360px, 키보드 이동·확대 상태를 확인했다.
- [ ] 공개 화면에 비공개 답변·파일 주소·내부 의견이 없다.

외부 제품의 공식 문서에서 확인한 기능 패턴과 이를 바탕으로 한 설계 해석:

- [GitHub Pull request reviews](https://docs.github.com/en/pull-requests/reference/pull-request-reviews): 코멘트·승인·수정 요청을 별개 검토 결과로 제공한다. HAVE에서는 검토 결정에 명확한 문구를 쓰는 근거로 참고했다.
- [Linear Search](https://linear.app/docs/search): 검색과 상태·담당자 등의 필터를 제공한다. HAVE에서는 역할별 목록과 검색/필터 분리를 제안했다.
- [Adobe Acrobat 서명 검증](https://helpx.adobe.com/acrobat/desktop/e-sign-documents/manage-digital-signatures/validate-digital-sign.html): 서명의 검증 상세를 확인할 수 있다. HAVE의 별도 승인 효력·파일 비교 표시는 내부 요구사항을 함께 반영한 설계 제안이다.

이는 경쟁 제품의 시각 디자인을 복제하거나 실제 사용자 조사를 수행한 결과가 아니다. 청록 메인·빨강 서브는 사용자 요청을 반영했으며 구체적인 색조·치수·컴포넌트·내비게이션은 이 프로젝트를 위한 제안이다. 미리보기는 더미 데이터로 동작하는 설계 참고물이다.
